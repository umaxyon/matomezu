# 指摘改善事例

AI が案を出したあと、ユーザーの指摘で方向や中身が変わった事例。案から選んだだけのもの、規約の見落としを直しただけのものは書かない（決まりは AGENT.md の「指摘改善事例」）。

## 事例 No.1: 並べる領域の名前

- **提案内容:** 内包の作業で、形を並べる所を「形を並べる枠」と呼んで、名前の案を出した。
- **私からの返信指摘:** 「枠」が何を指すのかを逆に聞かれた。欲しいのは「アイテムを置ける領域」の総称で、箱の中の文字の領域は関係ない、と確かめられた。
- **結果:** 総称を「Frame」（アイテム Frame も同じ意味）、内包ボックスの中の子を置く所を「子の領域」にして、用語集に足した。
- **学び:** 名前を出す前に、その名前が指す実物（何を含み、何を含まないか）を先に言う。

## 事例 No.2: 用語集の行に具体を書いた

- **提案内容:** 用語集の「子の領域」の行に「（内包ボックスはキャプションと本文の下）」と、ある形での位置を書き添えた。
- **私からの返信指摘:** その括弧書きを外すように言われた。
- **結果:** 括弧書きを外し、意味だけの行にした。
- **学び:** 用語集には言葉の意味だけを書く。個々の形での見え方や位置は書かない。

## 事例 No.3: 規約に書く文面が細かすぎた

- **提案内容:** 内包の段 8 で、規約に書く項目を 4 つ出した（子の形・線の置き場所・形は子まで探す・Frame の決まり）。関数の名前・不具合の経緯・例外・括弧書きの説明を多く含めていた。
- **私からの返信指摘:** 4 つとも書くが、具体やカッコ書きの説明が多いので、規約として過不足ない簡潔な書き方を考えるように言われた。
- **結果:** 1 項目 1 行の決まりだけにした。外したのは、ほかの行や用語集で言えていること、関数の名前、経緯、作り方の話。規約の確認で「縮めない」が 2 通りに読めると出て、縮めないものを書いた文に直した。
- **学び:** 規約の文面は、決まりだけを書く。ほかの行や用語集で言えていることは繰り返さない。コードの名前・経緯・理由は書かない。短くしたら、何を指すかが 1 通りに読めるかを確かめる。

## 事例 No.4: 起動のときの失敗を画面で知らせようとした

- **提案内容:** 常駐の URL から開いて常駐につながらないときに、画面の真ん中に「常駐につながりません」と出す案を出して作った。インスタンスの前に描くので、規約の置き場所と色の決まりに合わず、例外を足すかを聞いた。
- **私からの返信指摘:** 起動できていないなら、利用者もおかしいと分かっているので伝える必要は無い。そこを考慮したものは作らず、規約に「起動中の失敗は除く」と書けばよい、と言われた。
- **結果:** 一言を出す所を外し、何も出さずにつながるまで待つ形にした。規約に、起動の途中の失敗は画面に出さないと書いた。
- **学び:** 知らせを足す前に、利用者がその状態をもう分かっているかを考える。分かっていることのために、規約の外の仕組みを作らない。

## 事例 No.5: 暫定の見た目を作り込んだ

- **提案内容:** 常駐とのつながりが長く切れたままのとき、暫定でと言われたブック名の部分の色を変える所まで作った。
- **私からの返信指摘:** 最終的にはアイコンなどに変える予定で、置き場所も未定なので、画面の側は作らずに保留にしてほしいと言われた。
- **結果:** 画面の変更と文言を戻し、切れていることを store に入れる所だけを残した。
- **学び:** 「暫定」と言われた見た目は、作る前に、今入れるのか、データだけ用意して保留にするのかを確かめる。

## 事例 No.6: ゴミ箱をアクションに入れるのに、受け取る形を変える案を推した

- **提案内容:** ゴミ箱の戻す・消すをアクションにするため、一覧が対象のアクションが受け取る物を `{ books, trash }` に変える案（案 A）を推した。ブックに時刻のフィールドを持たせる案（案 B）は、ゴミ箱のブックを除く処理が各所に要るとして退けた。規約にも「一覧のアクションはブックの一覧とゴミ箱を受け取る」「画面に出ているブックを AI が外すときは open-on-screen で断る」と書く案を出した。
- **私からの返信指摘:** 案 A は一覧の受け取り方として不自然。案 B も、ブックを取る共通の入口を作ればよいのではないか、と言われた。規約の文面には、どちらの行も、規約ではなく実装の仕様だと言われた。
- **結果:** 案 B で作った。ゴミ箱のブックはブックのフィールド `trashed` を持ち、画面のストアと常駐の入口で分ける。規約には、土台のフィールドの名前と、利用者だけのアクションを AI に見せないことだけを書いた。
- **学び:** 漏れを防ぐために型を変える案を出す前に、入口を 1 か所にまとめて済まないかを考える。規約には作り手が知らないと間違える決まりだけを書き、中の振り分け方やホストの断り方は書かない。

## 事例 No.7: 土台が読む利用者の設定の項目を、土台に持たせる案を出した

- **提案内容:** 利用者の設定をプラグインが足せるようにする D54 で、土台が読む言語・スキン・キーの割り当ての 3 つの項目を、土台が自分の SettingDef として持つ案（名前は `lang`・`skin`・`keys`）を出した。
- **私からの返信指摘:** SettingDef を土台が持つのは層の違反にならないのか、と聞かれた。また、言語やスキンは足した分だけ設定から選べるはずだ、という理解の確認があった。
- **結果:** 項目は base が持ち、3 つの項目にだけ役（lang・skin・keys）を付ける形にした。土台は id ではなく役で引く。言語・スキン・キーを足す側は、役を書かない。
- **学び:** 土台が読む値でも、定義を土台に置く前に、土台が具体の機能を持つことにならないかを考える。土台が名前で引く代わりに、役のような土台の言葉で引けないかを先に探す。

## 事例 No.8: 言語の項目の値を言語コードにしていた

- **提案内容:** 言語の項目の値を、今の言語の設定と同じく言語コード（`ja` など）にする前提で進めていた。
- **私からの返信指摘:** 公式とコミュニティ版の同じ言語のパックを入れ替えられる仕組みにしたい、言語を変えたら再起動して差し替える形が可能か見切りを付けたい、と言われた。
- **結果:** 値をパックの id（`matomezu:ja` など）にした。同じ言語のパックを並べて選び、読み直して差し替える仕組みは別の課題にする。
- **学び:** 選択肢の値を決めるときは、同じ種類の選択肢が並ぶ場合（同じ言語のパックが 2 つなど）でも区別できるかを確かめる。後から変えると、保存したデータの変換がまた要る。

## 事例 No.9: ロック中の制限を道具の切り替えだけで済ませようとした

- **提案内容:** ロック中に画面から変えられないようにする構造として、道具の定義に「見るだけの道具」の印を足し、ロック中は toolOf がハンドを返す案を出した。コマンドは performs の判断にロックを足し、ページ単位かはアクションの引数に page があるかで見分ける形にした。
- **私からの返信指摘:** 選択はできて中身をドロワーで見せる機能（D67）のように、もっと細かい粒度の制御が要る見込みが高い。将来はユーザーの権限による認可もあり得るので、道具をハンドに絞るだけでなく、アイテムやコマンドの単位でロックの状態を感知して反応する・しないを決められる仕組みまで考えてほしいと言われた。
- **結果:** アクションを使えるかの問い合わせ（inspect）に「どこに対して・誰が」を足し、頭に許可の段（PermissionDef、最初は base のロック）を並べる案にした。道具・コマンド・ビューの個々の操作は、どれもその答えを見て、薄くするか消すかを各自が決める。
- **学び:** 制限の仕組みは、目の前の症状を止める一番大きな単位（道具）で切らない。「使えるか・なぜか」を答える問い合わせを 1 つにし、反応は使う側に任せる形にする。将来の別の理由（権限など）が段を足すだけで入るかを確かめる。

## 事例 No.10: ディレクトリ構成図の鉛筆のキーを、ツリーの割り当てに合わせる案を出した

- **提案内容:** D24 ディレクトリ構成図の鉛筆のキーとして、ツリーにならい、Enter ですぐ下に同じ種類、Tab で選んでいるフォルダの中にファイルを足す案を出した（もう 1 つの案は、Enter で名前を書き、足すのは＋と右クリックだけ）。
- **私からの返信指摘:** Enter は名前を書く。d で兄弟のフォルダ、f で兄弟のファイルを足す。フォルダの上で Tab を押すと、フォルダとファイルのアイコンを縦に並べた小さな枠が出て、上下で選び Enter で子として作り、名前を書く状態にする、と言われた。枠は、選んだ行のすぐ横に出すことも選ばれた。
- **結果:** その割り当てで作った。行のすぐ横に枠を出すには、キーのコマンドから行の位置が分からないため、土台の「その場の編集」に、何をするかの名前を持たせた（Stage.editing を boolean | string に。用語集にも一文）。
- **学び:** 似たブックの操作をそのまま写さず、そのブックで何を一番よくするか（ここでは名前を書くことと、フォルダかファイルかを選ぶこと）からキーを考える。案に出す前に、そのブックの使われ方を言葉にして確かめる。

## 事例 No.11: 機能のためだけのフィールドまで規約に書こうとした

- **提案内容:** D54 の規約の案に、セレクトの選択肢の名前（`optionTitles`）と、値の形を機能台帳から組み立てる `describe` の書き方を入れていた。
- **私からの返信指摘:** 規約はプラグイン開発のマニュアルではないので、仕組みや構造にとって重要な要素でないなら書かなくていいのでは、と言われた。
- **結果:** 規約に書くのは、利用者の設定の項目の置き場所と id、土台が role で引くこと、`userOnly`、項目ごとのアクションを作らないこと、ホームのタイプが変えさせない項目を選べること、ビューは任意であることに絞った。`optionTitles` と `describe` は書かなかった。
- **学び:** 規約に書くかは「書かないと、作り手が層や定義の向きを破る間違いをするか」で決める。機能の使い方（フィールドの書き方）は、コードの型とコメントに任せる。

## 事例 No.12: 道具箱の形の格子を「形のパネル」と呼び、絵の形を言葉にしなかった

- **提案内容:** D58 で、道具箱の「形」のボタンで開く格子を「形のパネル」として用語集に足す案を出した。旧版から持ち込んだ足元に文字を書く絵は、art の中だけの呼び名として「絵の形」のままにし、用語にしない案にした。
- **私からの返信指摘:** 格子は「シェイプパネル」と呼ぶ。個々の絵も総称として「シェイプ」と呼ぶ。シェイプは入れ子にできず、文字を下に書くといった特徴を持つ、と言われた。そのあと、シェイプは絵だけで、中に文字を書く 8 つの形は含めないこと、画面のボタンの名前は「形」のままにすることを選ばれた。
- **結果:** 用語集の「ブックの中身」の表に「シェイプ」を、「画面」の表に「シェイプパネル」を足した。コメントとテストの「形のパネル」「絵の形」を、この 2 つの言葉に直した。
- **学び:** 新しく作った物の種類（ここでは、子を持たず文字を下に書く絵）は、一つのプラグインの中だけの物と見て呼び名を流さない。特徴で他と分けられる種類なら、言葉にするかをユーザーに聞く。既にある言葉（「形」・kind: "shape"）と範囲が重なるときは、どこまでを指すかも確かめる。

## 事例 No.13: データのアイテムを、表とグラフだけの箱として案に出した

- **提案内容:** D49 のデータのアイテムで、表のセルは文字で持ち、数として読めるものだけをグラフに使う案を出した。グラフの見た目の差し替えには触れず、文字はタイトルだけにした。2 つ目の表は、表の見た目のときに縦に並べる形で考えた。
- **私からの返信指摘:** 列は数と文字の型を厳格にスキーマで決め、混ざった列は許さない。空のセルも許さず、無い所は使う側が 0 を入れる。グラフの見た目と動きは差し替えられる仕組みにする。文字の領域は箱と同じ（キャプション・本文・本文の幅のつまみ・寄せ）にし、グラフとの上下を入れ替えられ、出さないこともできる。データを 2 つ持つのは、1 つのグラフに棒と折れ線を重ねるためで、表を縦に並べるためではない、と言われた。
- **結果:** 列に型（number・text）を持たせ、data-set はセルが列の型に合わなければ断るようにした。見た目と動きはテーマキー（CSS）で差し替える。重ねる形は、表は 1 つのまま、描くもの（series）を並べて持つ案 A にした（横軸の違う表を重ねると、空のセルを許さない決めごとと噛み合わないため）。箱と共に使う文字の部分は base に移す。
- **学び:** グラフは「読めた値だけ描く」と緩くすると価値が無くなる。データを持つアイテムでは、まず値の型を厳格に決める案から出す。「複数持てるように」と頼まれたら、何のために複数にするのか（ここでは重ねて描くため）を先に確かめてから形を決める。

## 事例 No.14: コマンドの stage に pan を残し、規約の方を直す案を推した

- **提案内容:** E40 で、プラグインに見せる StageView から紙をずらす量（pan）を外した。そのとき、コマンドが受け取る stage にだけ pan を残す案 A を推した。これは規約の「コマンドが受け取るステージも同じ物」と食い違うので、規約の方を直す案だった。もう 1 つの案 B は、pan が要るコマンドに ctx.workspace からステージを探させる形で、書き手の手間と中の状態の見えすぎを理由に退けていた。
- **私からの返信指摘:** pan を取り出すのは toPaper の側でできるのでは、と問われた。
- **結果:** ctx を受け取って中で pan を探し、紙の上の点に直す関数 toPaperIn をプラグイン API に足した（案 B'）。コマンドの stage は見た目と同じ物のままにし、規約は直さなかった。
- **学び:** 規約と食い違う形を推す前に、食い違いを API の側で吸収できないかを考える。「呼ぶ側が探す手間」が難点なら、探す所を関数にまとめて出す案も並べる。
