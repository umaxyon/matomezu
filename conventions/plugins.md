# プラグイン

プラグインは、定義（ブックのタイプ・アイテム・アクション・テーマ・紙・コマンド・ダイアログ・文言）の束。配る単位で、登録する単位。
ビルトインプラグインも、追加プラグインと同じ口で登録する。

## プラグインどうしの関係

- プラグインは互いに独立している。ほかのプラグインを読まない
- 追加プラグインは、プラグイン API（`matomezu`・`matomezu/ui`・`matomezu/catalog`）だけを読む。テストで組むときだけ `matomezu/testing` も読む（見本は `test/rules.test.ts` が見張る）
- プラグイン API が出す名前の一覧は `test/plugin-api.test.ts` に書く。足すときも消すときもここを直し、わざと変えたと分かるようにする
- 例外は `base`。画面の骨組み・ダイアログの枠と入力のコンポーネント・紙・標準のテーマを持ち、ほかのプラグインは `base` の入口（`plugins/base/index`・`plugins/base/ui`）を読んでよい
- 別のプラグインの定義を使うときは、読むのではなく id で選ぶ（ブックのタイプがアイテム・アクション・道具の組を選ぶのと同じ形）
- あるタイプを、ほかのタイプとの差分として作らない。タイプはそれぞれ、使う物を id で選んで持つ

## 何をどこに置くか

- ブックのタイプのプラグインは `plugins/books/<名前>/` に置く。持つのは、タイプ 1 つと、そのタイプだけが使う物（そのタイプにしか無い画面・アクション・コマンド・ダイアログ）
- アイテムとアクションは、ブックのタイプとは別に定義する。いくつかのタイプが使う物は、ブックのタイプのプラグインに置かない
- `ui/` には画面に出ない仕組みだけを置き、画面に出る物は全部プラグインに置く
- ビルトインプラグインの並びは `plugins/index.ts` の `BUILTIN`（React なしのインスタンス用）と `plugins/ui.ts` の `BUILTIN_UI`（画面のあるインスタンス用）。既定の配置 `DEFAULT_LAYOUT` も `plugins/ui.ts`

## プラグインの中の形

- 入口は `index.ts`（React なし。プラグインの定義と、末尾で機能台帳の型の側への書き足し）と `ui.tsx`（見た目を結ぶ `definePluginUi`）
- 大きなプラグインは中を機能ごとのフォルダに分け、各フォルダにも同じ形（`index.ts`・`ui.tsx`・コンポーネント・`messages.ts`）で置く。プラグインの `index.ts`・`ui.tsx`・`messages.ts` が集める
- ブックのビューは `view/` に置く
- 同じプラグインの中は、下のフォルダも読める
- フォルダを動かしたら、機能台帳の型の側への書き足し（`declare module`）のパスも直す（ずれても誤りにならず、型が never になる）

## 機能台帳の型の側

- 機能台帳の型の側（`core/catalog.ts`。追加プラグインからは `matomezu/catalog`）の空の interface に、`declare module` で書き足す。id の型・ブックの型・引数の型はここから決まる
- 書き足しは `core/catalog.ts` そのものに向ける（名前を集め直すファイルに向けると、ほかの書き足しと合わさらない）
- `createMatomezu` には、型を書き足したプラグインを全部渡す。わざと減らすインスタンス（テストなど）は `partial: true`
- 取り込んだ追加プラグインは `createMatomezu` に渡さず、インスタンスの `use(追加プラグイン)` で足す（型の側に入らないので、型でなく組み立てで確かめる。`partial` は使わない）。`use` は渡した一覧で組み直し（前に足したものと置き換え）、状態を作ったときの初めに戻す。組み立てられない追加プラグインは外し、理由を返す。画面は、追加プラグインが変わると読み直して、起動のときに `use` する（取り込むのは利用者が確認のダイアログで許したときで、そのダイアログで読み直すことを知らせる）

## 見た目と差し替え

- `definePluginUi(plugin, { presentationViews, items, settingViews, dialogViews, widgets, commandIcons, overrides })` でビューを結ぶ。そのプラグインのブックのタイプ・アイテム・ダイアログに、ビューが無いと型の誤り
- 差し替えられるのはビュー（ブック・ダイアログ・ウィジェット）だけで、`overrides` に書く。アクションやブックのタイプなど中身は差し替えない
- 画面の配置（スロットにどのウィジェットを置くか、メニューの中身）は配置（`defineLayout`）に書く。配置は丸ごと替え、差分を重ねて混ぜない
- ブックのタイプによる出し分けは配置ではなく、ウィジェットが開いているブックを見て自分で決める

## 動的に取り込む

- 追加プラグインのフォルダには `matomezu.json` を置く。欄は `id`（プラグインの id）・`engine`（ホストのエンジンで動かす入口）・`ui`（画面で読む入口）・`pluginApi`（作ったときのプラグイン API の版）。入口はフォルダからのパスで、フォルダの外は指せない。知らない欄は誤り。【未実装】`pluginApi` は必ず書き、ホストが確かめる（下の版の決まり）
- `engine` の入口はプラグインを、`ui` の入口は見た目を結んだプラグインを `export default` で出す。`engine` の入口は React と `matomezu/ui` を読まない。`id` は `engine` の入口が出すプラグインの id と同じにする（組み立てで確かめる）
- 追加プラグインは、動いている常駐に足す・入れ替える（同じ id）・外すことができる。変えるたびにホストのエンジンを組み直し、画面は読み直す。組み直せなければ前のまま。起動のときに読めない追加プラグインは外して立て、理由を常駐のログに残す。AI は MCP の道具 `actions` で今使えるアクションを読み直す（MCP の道具の一覧は変わらない。definitions の「AI に見せる」）
- 追加プラグインは、プラグイン API の実装を中に持たない。ホストが変換する（Go に組み込んだ esbuild）とき、`plugin-modules` の表にある名前（`matomezu`・`matomezu/ui`・`react`・`react/jsx-runtime`）は取り込まず、動いている matomezu が渡す実物を使う（zod や React が 2 つになると動かないため）
- zod は `matomezu` から読む（`import { z } from "matomezu"`）。表に無い名前の import は、変換で誤りにする（zod の版も matomezu の約束に収めるため）
- 【未実装】プラグイン API は、matomezu とは別に版（semver）を持つ。名前を消す・変える、定義の欄や `ctx` の意味を変えるなどの壊す変更で大きな版、足すだけなら小さな版を上げる。追加プラグインは作ったときのプラグイン API の版を宣言し、ホストは読み込む前に比べて、合わなければ理由を返して読み込まない。開発者が手元に置く型の版は、プラグイン API の版と同じにする

## id と信頼

- 追加プラグインの id は npm のパッケージ名にし、定義の id はその頭を付ける（`definePlugin` が型で確かめる）
- プラグインは、入れる側が信頼して組み込むコード。id の頭や組み立ての確かめは、コードを隔てる仕組みではない
- 画面の側の追加プラグインは、画面と同じページで動き、画面ができることを全部できる（iframe などで隔てない。プラグイン API の実装を借りるため）。入れることが、画面ではそのプラグインを全部信頼すること
