# プラグイン

プラグインは、定義（ブックのタイプ・アイテム・アクション・テーマ・紙・コマンド・ダイアログ・文言）と、いくつもの定義が共に使うテーマキーの束。配る単位で、登録する単位。
ビルトインプラグインも、追加プラグインと同じ口で登録する。

## プラグインどうしの関係

- プラグインは互いに独立している。ほかのプラグインを読まない
- 追加プラグインは、プラグイン API（`matomezu`・`matomezu/ui`・`matomezu/catalog`）だけを読む。テストで組むときだけ `matomezu/testing` も読む（見本は `test/rules.test.ts` が見張る）
- プラグイン API の見た目の側（`matomezu/ui`）は、状態を丸ごと見せない。見た目は、matomezu が渡すステージの id から、フックで約束のものだけを引く:
  - データ: `useBook(stage)`・`usePage(stage)`（開いているブックとページ）、`useItem(stage, page, item)`（項目の型はアイテムの id で決まる）、`useShownPage(stage)`（ダイアログの下書きを重ねたページ。見せ方が描くのに使う）
  - ステージ: `useStage(stage)` は読むだけの `StageView`（`id`・`opened`・`zoom`・`pan`・`selection`・`placing`・`tool`・`pans`）。ブックのビューにはステージの id を渡す。コマンドの `ctx.stage` も同じ `StageView`
  - 定義と設定: `useCoreCatalog()`・`useUiCatalog()`（読むだけ）、`useSettings()`（言語とスキン）
  - データを変えるのはアクションだけ。ステージが開いているブックには `usePerform(stage)`、ほかの対象（一覧・設定）には `useActions()` の `perform` で行う。画面の状態（選択・ダイアログ・ページを開くなど）はコマンドと `useActions`
- プラグイン API が出す名前の一覧は `test/plugin-api.test.ts` に書く。足すときも消すときもここを直し、わざと変えたと分かるようにする
- 例外は `base`。画面の骨組み・ダイアログの枠と入力のコンポーネント・紙・標準のテーマを持ち、ほかのプラグインは `base` の入口（`plugins/base/index`・`plugins/base/ui`）を読んでよい
- ビルトインプラグインも、追加プラグインと同じプラグイン API で書く。base 以外は `plugin-api` と base の入口だけを読む（読み込みの向きは「構造と層」）。base は API の部品を作る側なので土台を読む
- ビルトインプラグインが使う土台の名前は、状態を丸ごと読む `ui/store-context` の物（`useMatomezuState`・`useCatalog`・`useUiCatalog`。代わりに上の状態を読むフックを使う。読むだけの `useCoreCatalog`・`useUiCatalog` は `ui/view-hooks` の物を出す）を除き、全部 `plugin-api` から出す。ビルトインの印（`defineBuiltin`）は `plugin-api/builtin` に置き、`plugin-entry` は出さない（印は、キーの割り当てでビルトインプラグインを先に扱うためだけのもので、id の決まりは変えない）
- base の入口には、プラグイン API に出してよい物だけを置く。迷う物は置く前にユーザーに確かめる
- プラグインに公開する共通の処理（ユーティリティ。経った時間の `elapsedOf` など）は、base の `utils` に置く。`utils/index.ts` で書き出した物は `matomezu` から、見た目の物（フックなど）を `utils/ui.ts` で書き出した物は `matomezu/ui` から、そのまま出る（入口は丸ごと出し直す）。`utils` に置かない base の物は出ない。足すときは置くだけで、出す物ごとに規約は書かない（出す名前の増減は `test/plugin-api.test.ts` の一覧で見える）
- 別のプラグインの定義を使うときは、読むのではなく id で選ぶ（ブックのタイプがアイテム・アクション・道具の組を選ぶのと同じ形）
- あるタイプを、ほかのタイプとの差分として作らない。タイプはそれぞれ、使う物を id で選んで持つ

## 何をどこに置くか

- ブックのタイプのプラグインは `plugins/books/<名前>/` に置く。持つのは、タイプ 1 つと、そのタイプだけが使う物（そのタイプにしか無い画面・アクション・コマンド・ダイアログ）
- アイテムとアクションは、ブックのタイプとは別に定義する。いくつかのタイプが使う物は、ブックのタイプのプラグインに置かない
- `ui/` には画面に出ない仕組みだけを置き、画面に出る物は全部プラグインに置く
- ビルトインプラグインの並びは `plugins/index.ts` の `BUILTIN`（React なしのインスタンス用）と `plugins/ui.ts` の `BUILTIN_UI`（画面のあるインスタンス用）。既定の配置 `DEFAULT_LAYOUT` も `plugins/ui.ts`

## プラグインの中の形

- 入口は `index.ts`（React なし。プラグインの定義と、末尾で機能台帳の型の側への書き足し）と `ui.tsx`（見た目を結ぶ `definePluginUi`）
- 大きなプラグインは中を機能ごとのフォルダに分け、各フォルダにも同じ形（`index.ts`・`ui.tsx`・コンポーネント・`messages.ts`）で置く。プラグインの `index.ts`・`ui.tsx`・`messages.ts` が集める
- ブックのビューは `view/` に置く
- 同じプラグインの中は、下のフォルダも読める
- フォルダを動かしたら、機能台帳の型の側への書き足し（`declare module`）のパスも直す（ずれても誤りにならず、型が never になる）

## 機能台帳の型の側

- 機能台帳の型の側（`core/catalog.ts`。追加プラグインからは `matomezu/catalog`）の空の interface に、`declare module` で書き足す。id の型・ブックの型・引数の型はここから決まる
- 書き足しは `core/catalog.ts` そのものに向ける（名前を集め直すファイルに向けると、ほかの書き足しと合わさらない）
- `createMatomezu` には、型を書き足したプラグインを全部渡す。わざと減らすインスタンス（テストなど）は `partial: true`
- 取り込んだ追加プラグインは `createMatomezu` に渡さず、インスタンスの `use(追加プラグイン)` で足す（型の側に入らないので、型でなく組み立てで確かめる。`partial` は使わない）。`use` は渡した一覧で組み直し（前に足したものと置き換え）、状態を作ったときの初めに戻す。組み立てられない追加プラグインは外し、理由を返す。画面は、追加プラグインが変わると読み直して、起動のときに `use` する。画面が取り込むときの確かめは、読み込み・見た目の組み立て・置いた配置まで含め、どれかで失敗した追加プラグインだけを外す（ほかのプラグインとブックは使える）

## 見た目と差し替え

- `definePluginUi(plugin, { presentationViews, items, settingViews, dialogViews, widgets, commandIcons, toolIcons, overrides })` でビューを結ぶ。そのプラグインのブックのタイプ・アイテム・ダイアログ・道具に、ビューやアイコンが無いと型の誤り
- 差し替えられるのはビュー（ブック・ダイアログ・ウィジェット）だけで、`overrides` に書く。アクションやブックのタイプなど中身は差し替えない
- 画面の配置（スロットにどのウィジェットを置くか、メニューの中身）は配置（`defineLayout`）に書く。matomezu/testing でアプリを組むときは、配置は丸ごと替え、差分を重ねて混ぜない
- 配置が名指したウィジェット・コマンド・スロット・メニューのうち、持ち主のプラグイン（id の頭）が組み込まれていない物は、その行だけ飛ばし、注意 N010 を残す。持ち主が組み込まれているのに無い物は誤り（E207〜E213）。画面の注意は `useLayoutNotices` で読む
- 追加プラグインは、置いてほしい所を定義に書く: ウィジェットは `place`（置けるスロットのうち 1 つ）、コマンドは `place`（入れるメニューと右クリックのメニュー）。動いている matomezu の画面は、既定の配置の末尾に、取り込んだ順に足す（並びの中の位置は書かない。並べ替えは利用者がする）
- ブックのタイプによる出し分けは配置ではなく、ウィジェットが開いているブックを見て自分で決める

## 見本

- 追加プラグインの見本は `test/added-plugins/ex1`・`ex2`…（連番）。どれも開発者プロジェクトと同じ形（`matomezu.json`・入口・自分の `tsconfig.json`・matomezu/testing を使う自分のテストと型の確かめ `test/`）で、自分の書き足しだけが入る TypeScript のプロジェクトにする
- プラグイン API の定義の種類は、どれかの見本が使う。【保留】見せ方（`definePresentation`）は、紙の無いページ（残課題図 D57）が決まるまで見本を持たない。作り手の違う見本どうしの確かめと保存・読み直しは、見本を常駐に読ませる e2e（`e2e/plugins`）で行う

## 動的に取り込む

- 追加プラグインのフォルダには `matomezu.json` を置く。欄は `id`（プラグインの id）・`engine`（ホストのエンジンで動かす入口）・`ui`（画面で読む入口）・`pluginApi`（作ったときのプラグイン API の版）。入口はフォルダからのパスで、フォルダの外は指せない。知らない欄は誤り
- `engine` の入口はプラグインを、`ui` の入口は見た目を結んだプラグインを `export default` で出す。`engine` の入口は React と `matomezu/ui` を読まない。`id` は `engine` の入口が出すプラグインの id と同じにする（組み立てで確かめる）
- 追加プラグインは、動いている常駐に足す・入れ替える（同じ id）・外すことができる。変えるたびにホストのエンジンを組み直し、画面は読み直す。組み直せなければ前のまま。起動のときに読めない追加プラグインは外して立て、理由を常駐のログに残す。AI は MCP 公開ツール `actions` で今使えるアクションを読み直す（MCP 公開ツールの一覧は変わらない。definitions の「AI に見せる」）
- 追加プラグインは、プラグイン API の実装を中に持たない。ホストが変換する（Go に組み込んだ esbuild）とき、`plugin-modules` の表にある名前（`matomezu`・`matomezu/ui`・`react`・`react/jsx-runtime`）は取り込まず、動いている matomezu が渡す実物を使う（zod や React が 2 つになると動かないため）
- zod は `matomezu` から読む（`import { z } from "matomezu"`）。表に無い名前の import は、変換で誤りにする（zod の版も matomezu の約束に収めるため）

## id と信頼

- プラグインの id は npm のパッケージ名（ビルトインプラグインは `@matomezu/<名前>`）。足す物の id は `<プラグインの id>:<名前>`（definitions の「id」）
- プラグインは、入れる側が信頼して組み込むコード。id の頭や組み立ての確かめは、コードを隔てる仕組みではない
- 画面の側の追加プラグインは、画面と同じページで動き、画面ができることを全部できる（iframe などで隔てない。プラグイン API の実装を借りるため）。入れることが、画面ではそのプラグインを全部信頼すること
