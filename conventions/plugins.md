# プラグイン

プラグインは、定義（ブックのタイプ・アイテム・アクション・テーマ・紙・コマンド・ダイアログ・文言の組・テーマキーなど）の束。配る単位で、登録する単位。
ビルトインプラグインも、追加プラグインと同じ口で登録する。

## プラグインどうしの関係

- プラグインは、ほかのプラグインのコードを読まない。読んでよいのは、プラグイン API（ビルトインプラグインは base の入口も）と、ほかのプラグインの連携ポイント（`import type` で、型だけ）
- 追加プラグインが読むプラグイン API は `matomezu`・`matomezu/ui`・`matomezu/catalog`。テストで組むときだけ `matomezu/testing` も読む（見本は `test/rules.test.ts` が見張る）
- プラグイン API の見た目の側（`matomezu/ui`）は、状態を丸ごと見せない。そこを使うコンポーネントは、matomezu が渡すステージの id から、フックで約束の物だけを引く（ブックのビューにはステージの id を渡す）
- ステージは、読み取り専用でプラグインに提供される。提供されるのは、コンポーネントとコマンドが描く・決めるのに要る物だけで、ステージのそれ以外の状態（表示領域の大きさ・道具のアイコンを開いているかなど）は提供されない。コマンドが受け取るステージも同じ物
- 見せ方は、ダイアログの下書き（設定の項目と形の項目の、まだ確定していない値）を重ねたブックとページで描く
- 機能台帳と、利用者の設定（言語・スキン・文字の色の上書きなど）も、読み取り専用でプラグインに提供される
- データを変えるのはアクションだけ。画面の状態（選択・その場の編集・ダイアログ・ページを開くなど）は、コマンドと `useActions` で変える
- ステージの選択は、開いているページの中の id を持つ物（アイテム・形の中身・ページのフィールドの中の物）の id を持つ。選択を読むコマンドとビューは、自分の扱わない物の id が混じるものとし、扱う物だけかを確かめてから使う
- プラグイン API が出す名前と、見せるステージのフィールドと、コマンドの run が受け取る文脈と操作（`CommandActions`）のフィールドの一覧は `test/plugin-api.test.ts` に書く。足すときも消すときもここを直し、わざと変えたと分かるようにする
- 例外は `base`。ほかのビルトインプラグインは `base` の入口（`plugins/base/index`・`plugins/base/ui`）を読んでよい
- ビルトインプラグインも、追加プラグインと同じプラグイン API で書く。base 以外は `plugin-api` と base の入口だけを読む（読み込みの向きは「構造とクレート」）。base は API の部品を作る側なので土台を読む
- プラグイン API は、状態を丸ごと読むフックを出さない（base 以外のビルトインプラグインも、状態は上のフックで約束の物だけを引く）。ビルトインの印（`defineBuiltin`）は `plugin-api/builtin` に置き、`plugin-entry` からは出さない（印は、キーバインドでビルトインプラグインを先に扱うためだけのもので、id の決まりは変えない）
- base の入口には、プラグイン API に出してよい物だけを置く。迷う物は置く前にユーザーに確かめる。base の入口の名前は、base のプラグインそのものを除き、どれもプラグイン API にも出す（`test/plugin-api.test.ts` が見張る）
- どの機能にも属さない、プラグインに公開する共通の処理（ユーティリティ。経った時間の `elapsedOf` など）は、base の `utils` に置く。`utils/index.ts` で書き出した物は `matomezu` から、見た目の物（フックなど）を `utils/ui.ts` で書き出した物は `matomezu/ui` から、そのまま出る（入口は丸ごと出し直す）。base の機能のフォルダ（置く計算・文字など）の物は、base の入口に置いた物を `plugin-entry` が一つずつ書いて出し直す。出す物を足すときに、物ごとに規約は書かない（出す名前の増減は `test/plugin-api.test.ts` の一覧で見える）
- 別のプラグインの定義を使うときは、読むのではなく id で選ぶ（ブックのタイプがアイテム・アクション・道具の組を選ぶのと同じ形）
- あるタイプを、ほかのタイプとの差分として作らない。タイプはそれぞれ、使う物を id で選んで持つ

## 何をどこに置くか

- ブックのタイプのプラグインは `plugins/books/<名前>/` に置く。持つのは、タイプ 1 つと、そのタイプだけが使う物（そのタイプにしか無い画面・アクション・コマンド・ダイアログ）
- アイテムとアクションは、ブックのタイプとは別に定義する。いくつかのタイプが使う物は、ブックのタイプのプラグインに置かない
- アイテムのプラグインは `plugins/items/<名前>/` に置く。持つのは、アイテム（いくつでも）と、それらのアイテムだけが使う物（アクション・設定の項目・テーマキーなど）
- base のほかに、ブックのタイプにもアイテムにも当たらない物（いくつものタイプが使う見せ方と、その見せ方だけが使う道具・アクションなど）は `plugins/<名前>/` に置く
- `ui/` には画面に出ない仕組みだけを置き、画面に出る物は全部プラグインに置く
- ビルトインプラグインの並びは `plugins/index.ts` の `BUILTIN`（React なしのインスタンス用）と `plugins/ui.ts` の `BUILTIN_UI`（画面のあるインスタンス用）。既定の配置 `DEFAULT_LAYOUT` も `plugins/ui.ts`

## プラグインの中の形

- 入口は `index.ts`（React なし。プラグインの定義）と `ui.tsx`（見た目を結ぶ `definePluginUi`）
- 大きなプラグインは中を機能ごとのフォルダに分け、各フォルダにも同じ形（`index.ts`・`ui.tsx`・コンポーネント・`messages.ts`）で置く。プラグインの `index.ts`・`ui.tsx`・`messages.ts` が集める（文言の表は `joinMessages` で 1 つにする。スプレッドで重ねると、同じ鍵の訳が黙ってあとの表で上書きされる）
- ブックのビューは `view/` に置く
- 同じプラグインの中は、下のフォルダも読める
- フォルダを動かしたら、`core/catalog.ts` への書き足し（`declare module`）のパスも直す（ずれても誤りにならず、型が never になる）
- 画面とは別の処理の流れ（Web Worker）で動かすファイルを持てるのは base だけ。そのファイルは、見た目でないファイルと同じ物だけを読み、ほかのファイルからは型だけ読まれる

## `core/catalog.ts`

- `core/catalog.ts`（追加プラグインからは `matomezu/catalog`）の空の interface（`ItemTable` など）に、`declare module` で書き足す。id の型・ブックの型・引数の型はここから決まる
- 書き足しは `core/catalog.ts` そのものに向ける（名前を集め直すファイルに向けると、ほかの書き足しと合わさらない）
- `createMatomezu` には、型を書き足したプラグインを全部渡す。型を書き足したプラグインを全部は渡さないインスタンスと、型を書き足していないプラグインも渡すインスタンス（どちらもテストなど。取り込んだ追加プラグインではない）は `partial: true`
- 取り込んだ追加プラグインは `createMatomezu` に渡さず、インスタンスの `use(追加プラグイン)` で足す（matomezu 本体の `core/catalog.ts` の型に入らないので、型でなく組み立てで確かめる。`partial` は使わない）。`use` は渡した一覧で組み直し（前に足したものと置き換え）、状態を作ったときの初めに戻す。組み立てられない追加プラグインは外し、理由を返す。画面は、追加プラグインが変わると読み直して、起動のときに `use` する。画面が取り込むときの確かめは、読み込み・見た目の組み立て・置いた配置まで含め、どれかで失敗した追加プラグインだけを外す（ほかのプラグインとブックは使える）

## 見た目と差し替え

- `definePluginUi(plugin, { presentationViews, items, connectors, settingViews, userSettingViews, dialogViews, widgets, commandIcons, toolIcons, overrides })` でビューを結ぶ。そのプラグインのブックのタイプ・アイテム・ブックの設定の項目・ダイアログ・道具に、ビューやアイコンが無いと型の誤り。利用者の設定の項目のビュー（`userSettingViews`）は書かなくてよい
- 利用者の設定の項目のビュー（`userSettingViews`）のうち、名前と入力Form の 1 行で描く物は、行を base の `SettingRow` で作る（名前の幅などを写さない）
- 差し替えられるのはビュー（ブック・ダイアログ・ウィジェット）だけで、`overrides` に書く。アクションやブックのタイプなど中身は差し替えない
- 画面の配置（スロットにどのウィジェットを置くか、メニューの中身）は配置（`defineLayout`）に書く。matomezu/testing で matomezu を組むときは、配置は丸ごと替え、差分を重ねて混ぜない
- 配置が名指したウィジェット・コマンド・スロット・メニューのうち、持ち主のプラグイン（id の頭）が組み込まれていない物は、その行だけ飛ばし、warning を残す。持ち主が組み込まれているのに無い物は error。画面の warning は `useLayoutWarnings` で読む
- 追加プラグインは、置いてほしい所を定義に書く: ウィジェットは `place`（置けるスロットのうち 1 つと、並びの中ですぐ前に置く `before` か、すぐ後ろに置く `after` のどちらか 1 つのウィジェットの id）、コマンドは `place`（入れるメニュー・右クリックのメニュー・配置の `anchorMenu`）。動いている matomezu の画面は、既定の配置に取り込んだ順に足す。位置を書かなければ末尾に足す。名指せるのは並びにあるウィジェットだけで、名指したウィジェットが並びに無いか、両方書いてあれば置かず、warning を残す。並べ替えは利用者がする
- ブックの見た目の重なりは、スロット `@matomezu/base:book-layers` に置くウィジェット（レイヤー）で描く。並べた順に下から重ねる。紙の座標で描くレイヤーは `PaperFrame` の中に描く
- 中身（リストの行・節など）を描くビューは、その要素に `useAnchorRef` でアンカーを付ける。アイテムには、アイテムを置くビューが付ける。1 つの id に付ける要素は 1 つだけ。アンカーの無い物のそばには、スタンドを立てられない
- ブックのレイヤー（`@matomezu/base:book-layers`）に描く物のうち、中身をホイールでスクロールさせる物は、CSS の overflow を `auto` か `scroll` にして、ブラウザのスクロールで動かす（ステージは、`auto`・`scroll` でまだスクロールできる物の上では紙をずらさない）。ホイールを自分で受ける物（overflow を `hidden` のまま scrollTop などを自分で動かす物、SVG や canvas を自分で動かす物）は、React の `onWheel` で `stopPropagation` し、紙に渡さない
- 中の物の見え方を自分で変えるビュー（中のスクロールなど）は Revealable を実装し、プラグイン API の `useRevealable` で名乗り出る。`reveal` は画面の上の見え方だけを変えてブックのデータは変えず、返ったときには物の位置が決まっているようにする（あとで終わる、なめらかなスクロールにしない）。ほかのプラグインが描いた物を見せるときは、そのビューの中に手を入れず、物を囲む Revealable に頼む
- 可変ページを描く見せ方のビューは、描く広さ（印刷区画を並べた広さ）を `useStageArea` でステージに知らせる。知らせなければ、ステージは紙 1 枚として扱う。形の位置をデータに持たず、並べ方から決める見せ方（ツリーなど）は、中身を右・下へずらした量（印刷区画の数）も一緒に知らせる
- 刷るのは、コマンドの操作の `requestPrint` で頼む
- 印刷プレビューと印刷で中身を描くには、見せ方のビューの定義に `printSheet`（印刷区画 1 つのビュー）を書く。無ければ白紙。描いて測ってから印刷区画に切る見せ方（マークダウンなど）は、測るだけのビュー `printMeasure` も書き、測った結果を知らせる
- 見せ方の定義の `seen` は、開いているページの物（最上位のアイテムか子の形）が、ステージの表示領域に見えているかを答える。無ければ、まだ見ていない変更は、開いているページの物なら見えたとする。ブックとページのフィールドの変更は、`seen` に聞かず、開いていれば見えたとする
- 見せ方の定義に `paper: false` を書くと、ステージは紙を置かない。そのビューは描く広さとスクロールを自分で持ち、可変ページでも `useStageArea` で広さを知らせない
- id を持つ物のそばに出し、倍率で大きさを変えずに付いて動く物は、base のスタンドのレイヤーに `Stand` で描く。スタンドを描く所はスタンドのレイヤーだけ。スタンドを出すだけのウィジェットは `@matomezu/base:book-layers` に置いてよいが、自分では描かず `Stand` を使う。スタンドを出したビューは、スタンドの中の操作が自分に届くことを当てにしない。閉じ方は、スタンドを出したビューが決める
- id を持つ物の右上の角に出す物（コーナーステータス）は、`Stand` を立てずに `AtCorner` で出す（base が物ごとにまとめて出す）。種類ごとに、base のスロット `@matomezu/base:corner-statuses` に置くウィジェット（`defineCornerStatus`。名前が要る）で名乗り、`AtCorner` はその id を名指す。出す・消すのは `AtCorner` を出したビューが決め、まとめた見た目の開け閉めは base が決める（上の「閉じ方は、スタンドを出したビューが決める」の例外）
- ブックのタイプによる出し分けは配置ではなく、ウィジェットが開いているブックを見て自分で決める
- ステージの上に浮かぶスロットは、上の行（`@matomezu/base:stage-top`。左上）と右上の角（`@matomezu/base:stage-corner`）。そこに置いたウィジェットはスロットが浮かべるので、自分で位置を決めない。ほかに、ステージの枠を基準に位置を決めて浮かべるウィジェットは、スロット `@matomezu/base:stage-body` に `@matomezu/base:book-view` と並べて置く。ブックの中身のビューの中には置かない。紙の座標で描く物はレイヤーにする。ポインタの所に出す物（道具のアイコンなど）は画面の座標で位置を決めるので、`root` に置く
- 右サイドパネルに出す物は、スロット `@matomezu/base:right-side-panel` に置くウィジェットにし、幅はそのウィジェットの定義の `rightSidePanel` に書く。開け閉めはプラグイン API の右サイドパネルのフック（`useOpenRightSidePanel` など）でし、自分で開け閉めや幅の動きを作らない
- 左サイドパネルに出す物は、スロット `@matomezu/base:left-side-panel` に置くタブのウィジェットにし、`defineLeftSidePanelTab` で作る（タブの名前が要る。追加プラグインは `place` で置いてほしいと書く）。開け閉めはプラグイン API の左サイドパネルのフック（`useOpenLeftSidePanel` など）でし、自分で作らない
- 設定画面に設定カテゴリを足すときは、スロット `@matomezu/base:settings-categories` に置くウィジェットにし、`defineSettingsCategory` で作る（追加プラグインは `place` で置いてほしいと書く）。配置に置いた設定カテゴリのどれも名指していない利用者の設定の項目は、base の「全体」に並ぶ
- 右サイドパネルが選択に従う中身を出している間（`useFollowsSelection`）、物を押して選ぶビューは、押しても選ぶだけにし、ドラッグで動かさない。Mod で足す・外すときは、階層の違う物も、持ち主の形に置き換えずにそのまま選ぶ

## 見本

- 追加プラグインの見本は `test/added-plugins/ex1`・`ex2`…（連番）。どれも開発者プロジェクトと同じ形（`matomezu.json`・入口・自分の `tsconfig.json`・matomezu/testing を使う自分のテストと型の確かめ `test/`）で、自分の書き足しだけが入る TypeScript のプロジェクトにする
- プラグイン API の定義の種類は、どれかの見本が使う。作り手の違う見本どうしの確かめと保存・読み直しは、見本を常駐に読ませる e2e（`e2e/plugins`）で行う

## 動的に取り込む

- 追加プラグインのフォルダには `matomezu.json` を置く。フィールドは `id`（プラグインの id）・`engine`（ホストのエンジンで動かす入口）・`ui`（画面で読む入口）・`pluginApi`（作ったときのプラグイン API の版）。入口はフォルダからのパスで、フォルダの外は指せない。知らないフィールドは error
- `engine` の入口はプラグインを、`ui` の入口は見た目を結んだプラグインを `export default` で出す。`engine` の入口は React と `matomezu/ui` を読まない。`id` は `engine` の入口が出すプラグインの id と同じにする（組み立てで確かめる）
- 追加プラグインは、動いている常駐に足す・入れ替える（同じ id）・外すことができる。変えるたびにホストのエンジンを組み直し、画面は読み直す。組み直せなければ前のまま。起動のときに読めない追加プラグインは外して立て、理由を常駐のログに残す。AI は MCP 公開ツールの `actions` で今使えるアクションを読み直す（MCP 公開ツールの一覧は変わらない。definitions の「AI に見せる」）
- 追加プラグインは、プラグイン API の実装を中に持たない。ホストが変換する（Go に組み込んだ esbuild）とき、`plugin-modules` の表にある名前（`matomezu`・`matomezu/ui`・`react`・`react/jsx-runtime`）は取り込まず、動いている matomezu が渡す実物を使う（zod や React が 2 つになると動かないため）
- zod は `matomezu` から読む（`import { z } from "matomezu"`）。表に無い名前の import は、変換で error にする（zod の版も matomezu の約束に収めるため）

## id と信頼

- プラグインの id は npm のパッケージ名（ビルトインプラグインは `@matomezu/<名前>`）。足す物の id は `<プラグインの id>:<名前>`（definitions の「id」）
- プラグインは、入れる側が信頼して組み込むコード。id の頭や組み立ての確かめは、コードを隔てる仕組みではない
- 画面の側の追加プラグインは、画面と同じページで動き、画面ができることを全部できる（iframe などで隔てない。プラグイン API の実装を借りるため）。入れることが、画面ではそのプラグインを全部信頼すること
