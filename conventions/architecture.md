# 構造とクレート

## クレート

`web/src` の下を、役割ごとのクレートに分ける。`web/src` の直下には、表のクレートと画面の入口（`main.tsx`）・`css.d.ts` だけを置く。

| クレート | 役割 | 読んでよいもの |
|---|---|---|
| `core` | データの形・定義の型・core 台帳・純粋な関数。React も状態も持たない | `core`・zod |
| `store` | 状態（Zustand）・コマンド・ダイアログの表・台帳アセンブル | `core`・`store`・zustand |
| `ui` | 画面の根と、プラグインが使う画面の口。画面に出る物は置かない | `core`・`store`・`ui`・React・zustand |
| `host-client` | ホストクライアント: 画面がホスト（常駐サーバー）とブラウザ（保存・URL・履歴・クリップボード・印刷）に頼む口 | `core`・`store`・`host-client`・zod |
| `engine` | ホストのエンジン: ホストの goja で、画面と同じアクションを行う入口 | `core`・`store`・`plugins`（ビルトインの一覧と、各プラグインの入口だけ）・`plugin-modules`・zod |
| `plugins` | 画面に出る物と、足していく定義の全部（ビルトインプラグイン） | 下の行（プラグインのファイルと、base 以外のビルトインプラグイン） |
| `plugin-api` | プラグイン API: 追加プラグインとビルトインプラグインが使ってよい名前を、土台から出し直すだけのクレート（`index.ts` は React なし、`ui.ts` は見た目、`builtin.ts` はビルトインだけが使うビルトインの印 `defineBuiltin`（キーバインドでビルトインを先に扱う）と、台帳アセンブルのときの確かめ（`checks`）を書く `CatalogCheckDef`・`problem`・`warning`、テーマキーに書かれた値の引き方 `writtenValues`） | `index.ts` は `core`・`store`、`ui.ts` は `ui`、`builtin.ts` は `store` |
| `plugin-entry` | プラグイン API の入口（`index.ts` が `matomezu`、`ui.ts` が `matomezu/ui`） | `index.ts` は `plugin-api`・zod（`z` を出し直す）・`plugins/base`（base の入口の名前を、一つずつ書いて出し直す）・`plugins/base/utils`（丸ごと出し直す）、`ui.ts` は `plugin-api/ui`・`plugins/base/ui`・`plugins/base/utils/ui`（丸ごと出し直す）。どちらもビルトインプラグインの一覧（`plugins`・`plugins/ui`）を型だけ読み、ビルトインが `core/catalog.ts` に書き足した物をいつも含める |
| `testing` | テストで組む入口（`matomezu/testing`）。テストのプロセスの中で組み、ホストは使わない。プラグイン API に含めない | `store`・`ui`・`plugins`（ビルトインプラグインの一覧） |
| `plugin-modules` | 追加プラグインが借りる、名前から実物を引く表（`index.ts` はホストのエンジン用、`ui.ts` は画面用） | `plugin-entry`・React |

- 土台（`core`・`store`・`ui`）は、プラグインを受け取って動かす枠と、その枠が決める言葉（ステージ・ページ・置いたアイテムの外枠など）を持ち、具体的な機能は持たない。プラグインを読まない
- 土台の中に、プラグインしか使わない処理を置かない。そうした処理は base が持つ。core と store のモジュールで、プラグインしか読んでいない物が無いことを見張る（ui はプラグインが使う画面の口なので除く）
- ステージの状態（道具のアイコンを開いているか・背景を直しているか）と、その開閉の決まりは、ステージの言葉として土台に置く。土台自身も読む状態で、上の行の「プラグインしか使わない処理」には当たらない
- コマンドマッピングの `anchorMenu`（押した物にアンカーがあるとき、どの右クリックのメニューにも足すコマンドの並び）は、コマンドマッピングの言葉として土台に置く。アンカーを付ける・押した物のアンカーを見つける・メニューに足すのは base で、土台は並びを確かめて渡すだけ
- プラグイン（base を含む）が持つ画面の状態には、ステージごとの物と、ステージに結ばない窓の外観枠の状態（左サイドパネルの開閉など）がある。どちらも、土台の store の、プラグインの id ごとの置き場に置く。土台は中身を読まない。プラグインは自分の置き場だけを読み書きする。ビューは自分の kit を渡すフックで読み書きし、コマンドは文脈の `stageState`・`frameState` で読み、run が受け取る `updateStageState`・`updateFrameState` だけで変える（`useActions` の操作には入れない。持ち主はコマンドの id の頭のプラグイン。変えるステージの状態は呼ばれた場所のステージの物）。読み直しても戻したいステージの状態は、プラグインの `placedState`（`PlacedStateDef`）に書く（画面の場所に入り、URL に写る）。窓の外観枠の状態は画面の場所に入らず、読み直すと消える。URL やホストクライアントに自分で書かない
- 入口（`plugin-entry`・`testing`）は外に名前を出すだけで、中のコードは入口を読まない
- 例外は `plugin-modules`。`plugin-entry` を読んでよいのは `plugin-modules` だけで、`plugin-modules` を読んでよいのはホストのエンジン（`engine/engine.ts`）と画面の入口（`main.tsx`）だけ
- 向きは 土台 → `plugin-api` → ビルトインプラグインと `plugin-entry` → `plugin-modules` の一方向。`plugin-api` はプラグインを読まない（base の物を出し直すのは `plugin-entry`）
- プラグインのファイルは役割で見る。見た目（`.tsx` と `ui.ts`）は `ui` と同じものを読んでよく、ほかは `core`・`store`・zod だけ
- 表と上の行で読んでよい物（zod・React・zustand）のほかに読んでよい外のライブラリは次だけ: Markdown を読むライブラリ（mdast-util-from-markdown・mdast-util-gfm・micromark-extension-gfm と、その型の mdast）、コードを色付けするライブラリ（refractor と、その型の hast）。ライブラリごとに決めた 1 つのファイルだけが読み、その型をプラグイン API に出さない（matomezu の形に移して出す）
- 上の 2 行は base だけ。base 以外のビルトインプラグインは、`plugin-api` と base の入口だけを読み、土台を直に読まない。見た目は `plugin-api/ui`・`plugins/base/ui`・React も読み、見た目でないファイルは `plugin-api`・`plugins/base/index`・zod だけ。状態は `plugin-api/ui` のフック（plugins の「プラグインどうしの関係」）で読む。base はプラグイン API を読まない
- 見た目でないファイルは、見た目を読まない
- `web/src` のファイルどうしも、値で読む輪を作らない（型だけ読むのは除く）
- これらは `test/rules.test.ts` が見張る

## Go のパッケージ

`internal/` の下を、役割ごとのパッケージに分ける（`internal/` の外の Go は、実行ファイルの入口 `cmd/matomezu` と、埋め込む画面の `web` だけ）。読み込みの向きは一方向で、輪を作らない。

| パッケージ | 役割 | 読んでよいもの |
|---|---|---|
| `storage` | matomezu のデータ（ブック・設定など）の保存（SQLite）。ブックの中身は解釈しない | なし |
| `plugin` | 追加プラグインのフォルダ（`matomezu.json`）を読み、Go に組み込んだ esbuild で変換する | なし |
| `engine` | ホストのエンジン: `engine.js` を goja で動かし、アクション・組み直し・ブックとアノテーションの確かめを行う | `plugin` |
| `server` | ホスト: HTTP の口・知らせ（SSE）・窓・データをまとめる Hub | `engine`・`plugin`・`storage` |
| `mcp` | AI に matomezu を MCP 公開ツールとして渡すサーバー。ホストの AI の口（`/api/ai/...`）にだけ話す | なし |
| `home` | matomezu 保管庫フォルダ（利用者ごとに 1 つ） | なし |
| `browser` | URL を既定のブラウザで開く | なし |
| `web` | 実行ファイルに埋め込む画面（ビルドした `web/dist`） | なし |
| `cmd/matomezu` | 実行ファイルの入口。上のパッケージを組み合わせる | 全部（`web` も） |

- `mcp` は `server` を読まない。AI からの頼みは、人の画面と同じくホストの HTTP の口を通す
- これらは `test/rules.test.ts` が見張る
- `server` がブックの JSON から直に読んでよいのは、土台のフィールド（名前・ゴミ箱に入れた時刻・プロジェクト・ページの id と名前）だけ。アイテムやタイプのフィールドは読まず、中身の解釈はホストのエンジンに任せる（見張りは無い）

## 状態を変える所

- 状態を変えるのは `store` の中だけ（ほかで `setState` を使わない）
- データを変える入口はアクションだけ（画面の操作も AI の操作も同じアクションを通る。テストの用意を除く。「作業の進め方」の「テスト」）。常駐だけが使う記録（ブックを開いた時刻、参加者の様子など）は、アクションを通さず常駐が持つ
- 土台（core・store・ui）は、プラグインの物（アクションなど）を id で名指さない。アクションを行ってからステージで開く、のような組み合わせは、そのアクションを持つプラグインが関数で出す（base の `addPageIn`・`createBookIn`）。行うだけなら `perform`
- インスタンスの、`useActions` に入れない操作は、ホストクライアント・画面の入口（`main.tsx`）・土台のフックだけが使う。プラグインは、土台のフック（プラグイン API）と、コマンドの run が受け取る操作を通してだけ触る

## ホストとブラウザとのやり取り

- ホストとブラウザに触るのは `host-client` だけ
- 起動の途中の失敗（常駐につながらない）は画面に出さない（起動していないことは利用者に分かる）。常駐につながらなければ、つながるまで待つ。ただし、常駐は立っているのに、このブラウザが画面 cookie を持たず断られたときだけ、画面を組む前に 1 行（土台の文言）を出して止める（立っている常駐を待っても、利用者には原因が分からないため）
- 常駐の「画面から」の入口（HTTP）は、画面 cookie を持つブラウザの頼みだけを通す。AI の入口とは別で、AI は画面の入口を使えない。画面 cookie の鍵を渡す使い捨てのコードは、常駐がブラウザを開く URL にだけ載せ、どの返事にも載せない。入口を足すときは `screen` で包む（`rules.test` が見張る）
- 窓は、コントロールセンターかブックスクリーンのどちらかを前に出す（窓が前に出している物）。退いた物の中は残す。隠れているブックスクリーンの物は、見えていない物として分けて AI に知らせる
- 画面の場所は、ホストクライアントがブラウザの URL と行き来させる。ブック・ページの移動と分割する・やめるはブラウザの履歴に積み、ほかは（場所に入れる画面の状態も）書き換えるだけ。同じ同期の処理の中の移動は、まとめて 1 つ積む（await・setTimeout の後は別に積む）。選択と道具は入れない
- ホスト（常駐サーバー。Go）は、アクションを `web/src/engine/engine.ts` から作った `internal/engine/engine.js` で行う（ホストのエンジン）
- ホストは、つながっている窓ごとに、見ているものとフォーカスの順を覚える。AI の `view` と `show` は、見ているものを知らせた窓のうち最後にフォーカスされた窓に向ける。最後にフォーカスされた窓（開いた直後の窓など）がまだ知らせていなければ、上限の時間まで知らせを待つ
- ゴミ箱のブックとそのアノテーションは、AI の MCP 公開ツール（`list_books`・`read_book`・`read_page`・`view` が添える、AI の応えを待つ物・`show`）と CLI の `annotations` に出さない
- どこかの窓に出ているブック（隠れているブックスクリーンのブックも含む）を、AI はゴミ箱に入れられない（`open-on-screen` で断り、何も変えない。AI は利用者に聞く）。ブックを開いた時刻を残すのは、窓で見えたブックだけ
- どこかの窓で利用者が直している物（編集ロック）を、AI のアクションは変えも消しもしない（`being-edited` で断り、何も変えない）。利用者のアクションは編集ロックで止めない。ただし `lockedForUser` のアクション（変更提案郵便の反映など、直している最中に当てるとその直しで上書きされる物）は止める
- AI 編集チケットは、窓で見えたら閉じる。見られる前に利用者の戻す・やり直すで消えたら、消えたことを AI に渡す。アクションが失敗にした AI 編集チケットは、次に利用者が AI に話しかけたときに AI に渡る

## error

- 投げる error は `core/errors.ts` の表に番号（E と 3 桁）と文を書き、`problem`・`fail` で作る。ほかで `new Error` を作らない（同じクレートの中で捕まえる合図（`NoServer` など）は error ではないので除く）
- 台帳アセンブルの error では、ビルトインプラグインならインスタンスを作らず、追加プラグインならそのプラグインを外す。実行中の error は、その操作を止める
- 番号は一度付けたら変えず、消した番号も使い回さない。範囲は E0xx 定義の組の食い違い、E1xx 表に無いものを引いた・前提の状態が無い、E2xx 画面の組み立て、E3xx プラグイン、E4xx ホストとブラウザとのやり取り
- 文は開発者向けの英語で、画面には出さない
- アクションが断る理由（`unknown`・`not-allowed` など）は結果であって error ではないので、表に入れない

## warning

- warning は、その組み合わせ（プラグイン・ブック・UI マッピング）である間ずっと成り立つ問題に使う。画面で見つかっても常駐で見つかっても、そうした問題は warning に落とす。一度きりの出来事（アクションを断られた・通信が切れた・描くときの例外）は warning にしない（断りはトーストかダイアログ、error は E、調べるための記録はログ）
- 止めるほどではない間違い（その物だけ効かない）は、error にせず warning にする。warning は `core/warnings.ts` の表に番号（W と 3 桁）と文を書き、どのプラグインの warning かを添えて、台帳アセンブルが機能台帳に集める
- 番号の決まりと文は error と同じ（変えない・使い回さない・開発者向けの英語で画面には出さない）
- 追加プラグインの既定のキーバインドが、同じ範囲・同じキーのほかのプラグインのキーバインドに負けて効かないときは、warning にする（利用者のキーバインドに負けたときは warning にしない）
- ビルトインプラグインは warning を出さない（テストが見張る）
- 読めないブック（タイプが無い・形に合わない・アイテムどうしの決まりを守らない）も warning にする。warning にはブックの id と名前を添え、どのプラグインの warning かはタイプの持ち主。確かめる関数は core に 1 つだけ置き、画面もホストも使う
- 読めるが、機能台帳に無いアイテムや設定の項目を持つブックも、warning にする（どのプラグインの warning かは、無い物の持ち主）
- 画面だけで見つかる warning（UI マッピングで飛ばした物・`place` の `before`・`after` の書き方が合わずに置かなかったウィジェット・画面が組めずに外した追加プラグイン）は、ホストクライアントがホストに知らせる（前に知らせたものと入れ替え、つなぎ直すたびに知らせ直す）。知らせるのは番号と値だけで、文はエンジンが表から作る
- ホストは、問題を 1 か所にメモリで持つ: 定義の warning・読めないブック・warning のあるブック・画面が知らせた warning（窓ごと。窓が離れたら消す）。起動したときとプラグインが変わったときに全部のブックを、ブックが保存されたときにその 1 冊を確かめ直す（読めるかは今のプラグインで決まるので、DB には残さない）
- ホストは問題を、常駐のログ（変わったときに書く）と、AI の `list_books`（読めないブックに理由を添える）・`actions` に出す。AI が読めないブックにアクションを行うと、「無い」（`no-book`）でなく `unreadable` とその理由で断る
- 画面は読めないブックを捨てず、データには手を付けない
