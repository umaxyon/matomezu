# 構造とクレート

## クレート

`web/src` の下を、役割ごとのクレートに分ける。`web/src` の直下には、表のクレートと画面の入口（`main.tsx`）・`css.d.ts` だけを置く。`core`・`store`・`ui`・`host-client`・`engine` は自分のフォルダの中のファイルも読んでよく、表の「読んでよいもの」は、そのほかに読んでよい物。ファイルごとに書いた行（`plugin-api`・`plugin-entry`・`testing`・`plugin-modules`）は、その行のとおり。プラグインのファイルは、表の下の行のとおり。

| クレート | 役割 | 読んでよいもの |
|---|---|---|
| `core` | データの形・定義の型・core 台帳・純粋な関数。React も状態も持たない | zod |
| `store` | 状態（Zustand）・コマンド・ダイアログの表・台帳アセンブル | `core`・zustand |
| `ui` | 画面の根と、プラグインが使う画面の口。画面に出る物は置かない | `core`・`store`・React・zustand |
| `host-client` | ホストクライアント: 画面がホスト（常駐サーバー）とブラウザ（保存・URL・履歴・クリップボード・印刷）に頼む口 | `core`・`store`・zod |
| `engine` | ホストのエンジン: ホストの goja で、画面と同じアクションを行う入口 | `core`・`store`・`plugins`（ビルトインの一覧と、各プラグインの入口。表の下の「プラグインの外」の行）・`plugin-modules`・zod |
| `plugins` | 画面に出る物と、足していく定義の全部（ビルトインプラグイン） | 下の行（プラグインのファイルと、base 以外のビルトインプラグイン） |
| `plugin-api` | プラグイン API: 追加プラグインとビルトインプラグインが使ってよい名前を、土台から出し直すだけのクレート（`index.ts` は React なし、`ui.ts` は見た目、`builtin.ts` はビルトインだけが使うビルトインの印 `defineBuiltin`（キーバインドでビルトインを先に扱う）と、台帳アセンブルのときの確かめ（`checks`）を書く `CatalogCheckDef`・`problem`・`warning`、テーマキーに書かれた値の引き方 `writtenValues`） | `index.ts` は `core`・`store`、`ui.ts` は `ui`、`builtin.ts` は `store` |
| `plugin-entry` | プラグイン API の入口（`index.ts` が `matomezu`、`ui.ts` が `matomezu/ui`） | `index.ts` は `plugin-api`・zod（`z` を出し直す）・`plugins/base`（base の入口の名前を、一つずつ書いて出し直す）・`plugins/base/utils`（丸ごと出し直す）、`ui.ts` は `plugin-api/ui`・`plugins/base/ui`・`plugins/base/utils/ui`（丸ごと出し直す）。どちらもビルトインプラグインの一覧（`plugins`・`plugins/ui`）を型だけ読み、ビルトインが `core/catalog.ts` に書き足した物をいつも含める |
| `testing` | テストで組む入口（`matomezu/testing`）。テストのプロセスの中で組み、ホストは使わない。プラグイン API に含めない | `core`・`store`・`ui`・`plugins`（ビルトインプラグインの一覧） |
| `plugin-modules` | 追加プラグインが借りる、名前から実物を引く表（`index.ts` はホストのエンジン用、`ui.ts` は画面用） | `plugin-entry`・React |

- 土台（`core`・`store`・`ui`）は、プラグインを受け取って動かす枠と、その枠が決める言葉（スクリーン・ステージ・ページ・置いたアイテムの外枠など）を持ち、具体的な機能は持たない。プラグインを読まない
- 土台の中に、プラグインしか使わない処理を置かない。そうした処理は base が持つ。ただし、土台が外に出していない値（store の状態など）を読む物と、土台が確かめたことを根拠に型で示せない所を言い張る物は、プラグインしか使わなくても土台に置く。core と store のモジュールで、プラグインしか読んでいない物が無いことを見張る（ui はプラグインが使う画面の口なので除く）
- ステージの状態（道具のアイコンを開いているか・背景を直しているか）と、その開閉の決まりは、ステージの言葉として土台に置く。土台自身も読む状態で、上の行の「プラグインしか使わない処理」には当たらない
- コマンドマッピングの `anchorMenu`（押した物にアンカーがあるとき、どの右クリックのメニューにも足すコマンドの並び）は、コマンドマッピングの言葉として土台に置く。アンカーを付ける・押した物のアンカーを見つける・メニューに足すのは base で、土台は並びを確かめて渡すだけ
- プラグイン（base を含む）が画面の中で持つ状態は、プラグイン状態（`PluginStateDef`）として宣言する（ビューの中だけの一時の状態は「コードの書き方」の「データとビュー」）。範囲は、ステージ・スクリーン・窓（左サイドパネルの開閉など）のどれか。スクリーンの範囲の値は、開いた 1 枚ごとに持ち、閉じたら消える。値は土台の store の 1 か所に持ち、アクションのデータとは別で、アクションでは変えない。土台は値の中を読まない。ビューは kit と宣言を渡すフックで、コマンドは文脈の `pluginState` と run が受け取る `updatePluginState` で、スクリーンの定義と書庫アピアランスのメソッドは受け取る `read` で、自分の宣言だけを読み書きする（`useActions` の操作には入れない。持ち主は宣言の id の頭のプラグイン。ステージ・スクリーンの範囲の宣言は、呼ばれた場所のステージ・スクリーンの値。base のコマンドは、ほかのスクリーン（id で名指す）のスクリーンの範囲の自分の宣言にも値を入れられる（プラグイン API に出さない））。宣言は、値を画面の場所（URL に写る）に入れるか（`address`）を答える。入れるなら、読み直しても戻り、外から来る値を読むための形（zod）を持ち、土台は宣言の形で確かめる（合わない値と宣言の無い id は落とす）。ブラウザの履歴に積むかも宣言が答える。入れないなら、値の型だけを持ち、読み直すと消える（画面の場所を当てはめても残る）。ほかのプラグインの宣言に値を入れるのは、画面の場所に入れる宣言（`address` を持つ）に、宣言の id と値で入れる道（`useSetPluginStateById`。スクリーンの宣言は、書き先を呼んだビューのスクリーンか、スクリーンの定義の id で指す）だけ。base は、今の値が名指した値と同じときだけ入れるとも頼める（プラグイン API に出さない）。URL やホストクライアントに自分で書かない
- 入口（`plugin-entry`・`testing`）は外に名前を出すだけで、中のコードは入口を読まない
- 例外は `plugin-modules`。`plugin-entry` を読んでよいのは `plugin-modules` だけで、`plugin-modules` を読んでよいのはホストのエンジン（`engine/engine.ts`）と画面の入口（`main.tsx`）だけ
- プラグインの外（ビルトインの一覧 `plugins/index.ts`・`plugins/ui.ts`、ホストのエンジン、画面の入口、`testing`）がプラグインを読むときは、そのプラグインの入口（`index.ts`・`ui.tsx`（`ui.ts`））だけを読む（どのプラグインを読んでよいかは、表に行のある物は表の行のとおり）。中のファイルは、そのプラグインが組み直してよい所
- 向きは 土台 → `plugin-api` → ビルトインプラグインと `plugin-entry` → `plugin-modules` の一方向。`plugin-api` はプラグインを読まない（base の物を出し直すのは `plugin-entry`）
- プラグインのファイルは役割で見る。見た目（`.tsx` と `ui.ts`）は `ui` と、`ui` が読んでよいものを読んでよく、ほかは `core`・`store`・zod だけ
- 表と上の行で読んでよい物（zod・React・zustand）のほかに読んでよい外のライブラリは次だけ: Markdown を読むライブラリ（mdast-util-from-markdown・mdast-util-gfm・micromark-extension-gfm と、その型の mdast）、コードを色付けするライブラリ（refractor と、その型の hast）。ライブラリごとに決めた 1 つのファイルだけが読み、その型をプラグイン API に出さない（matomezu の形に移して出す）
- 上の 2 行は base だけ。base 以外のビルトインプラグインは、`plugin-api` と base の入口だけを読み、土台を直に読まない。見た目は `plugin-api/ui`・`plugins/base/ui`・react も読み（react-dom は読まない。追加プラグインが借りられる物と合わせる）、見た目でないファイルは `plugin-api`・`plugins/base/index`・zod だけ。状態は `plugin-api/ui` のフック（「プラグイン」の「プラグインどうしの関係」）で読む。base はプラグイン API を読まない
- 見た目でないファイルは、見た目を読まない
- `web/src` のファイルどうしも、値で読む輪を作らない（型だけ読むのは除く）
- これらはテストが見張る

## Go のパッケージ

`internal/` の下を、役割ごとのパッケージに分ける（`internal/` の外の Go は、実行ファイルの入口 `cmd/matomezu`、埋め込む画面の `web`、`clients/` の下（AI のプログラムごとの `clients/<AI の名前>`、ADE ごとの `clients/ade/<ADE の名前>`）、直して使う外のモジュールの写し `third_party/<モジュールのパスの最後の要素>`（matomezu のパッケージを読まない。写すのはユーザーと決めてから）だけ）。読み込みの向きは一方向で、輪を作らない。

| パッケージ | 役割 | 読んでよいもの |
|---|---|---|
| `storage` | matomezu のデータ（ブック・設定など）の保存（SQLite）。ブックの中身は、ページとフォルダの行に分けるための土台のフィールド（エントリの種類・id、フォルダの役〈`folderRole`〉）のほかは解釈しない（一度きりのデータの移し替えは除く） | なし |
| `plugin` | 追加プラグインのフォルダ（`matomezu.json`）を読み、Go に組み込んだ esbuild で変換する | なし |
| `engine` | ホストのエンジン: `engine.js` を goja で動かし、アクション・組み直し・ブックとアノテーションの確かめを行う | `plugin` |
| `server` | ホスト: HTTP の口・知らせ（SSE）・窓・データをまとめる Hub | `aiwire`・`engine`・`firewall`・`peer`・`plugin`・`storage` |
| `mcp` | AI に matomezu を MCP 公開ツールとして渡すサーバー。ホストの AI の口（`/api/ai/...`）にだけ話す | `aiwire` |
| `aiwire` | `mcp` とホストの AI の口で同じでなければならない値（ヘッダの名前など）。読み合えない 2 つが共に使う物だけを置く | なし |
| `peer` | ホストどうしのつなぎの部品: ホストの鍵とホスト id・ホストどうしの TLS・ホストどうしの入口の包み・リバース接続の張り方と受け方・常駐間通信プロトコルの版・接続確認コード・同じ LAN のホストを見つける（mDNS）・WSLプロキシ | なし |
| `firewall` | Windows のファイアウォールの、ホストどうしの入口と mDNS を受ける規則を読み書きする | なし |
| `home` | matomezu 保管庫フォルダと、npm の入口が版ごとに写した実行ファイルの置き場 | なし |
| `browser` | URL を既定のブラウザで開く | なし |
| `web` | 実行ファイルに埋め込む画面（ビルドした `web/dist`） | なし |
| `clients/<AI の名前>` | AI のプログラムごとの事情を抱える部品（その AI のプログラムに起こす知らせを渡すなど） | なし |
| `clients/ade/<ADE の名前>` | ADE ごとの事情を抱える部品（ADE のワークスペースの名前を読む・表示名を書くなど） | なし |
| `cmd/matomezu` | 実行ファイルの入口。上のパッケージを組み合わせる | 全部（`web`・`clients` も） |

- `mcp` は `server` を読まない。AI からの頼みは、人の画面と同じくホストの HTTP の口を通す
- `clients` を読むのは `cmd/matomezu` だけ
- これらはテストが見張る
- `server` がブックの JSON から直に読んでよいのは、土台のフィールド（ブックの名前、エントリの種類〈ページ・バインダ・ブック・フォルダ・参照エントリ〉・id・名前、参照エントリの指す先（`of` の種類と id）、ページのタイプ、バインダが入れるタイプ、バインダの中のページ、フォルダの行の役（`folderRole`）・システムフォルダの印（`systemFolder`）と並び、読めない物のフォルダの並びの要素が持つ元の要素（`entry`））と、役を名乗る種類（`SubjectDef` の `role`。「定義と機能台帳」の「アクション」）のレコードの、core が取り決めたフィールドだけ。アイテムやタイプのフィールドは読まず、中身の解釈はホストのエンジンに任せる（見張りは無い）

## AI の側に置く物

matomezu が配る AI ごとの部品（Claude Code のプラグインなど）は `clients/<AI の名前>/` に置き、その AI のプログラムの事情（プラグインの形・フック・会話への渡し方）を抱える。ほかの AI の部品は、`matomezu watch` の知らせを渡すコマンドの約束に合わせて、matomezu の外で作れる（matomezu が配る部品も、外の物に差し替えられる）。
起こす知らせの決まりと AI に見せる文は、常駐と、AI の種類を問わないコマンド（`matomezu watch` など）が持つ（その AI のプログラムに渡すための名前と、常駐メッセージの本文（返したフォローステップのプラグインが持つ）は除く）。

- 常駐は、起こす知らせのために AI のプログラムを起動しない。起こす知らせは、AI の側で受け取る
- 常駐と MCP は、AI の種類も ADE も知らない。ADE ごとの事情は `clients/ade/<ADE の名前>/` が持つ。AI のプログラムごとに違う受け取り方（1 行の長さなどの値と、知らせを渡すコマンド）は `clients/<AI の名前>/` が持ち、`matomezu <AI の名前>` のコマンドがそれで `matomezu watch`（`matomezu mcp`）を組み立てる。AI ごとの部品は、AI のプログラムから `matomezu <AI の名前>` を呼ぶ
- リフレッシュリクエスト（「定義と機能台帳」の「アクション」）は、会話を空にできる AI ごとの部品だけが受ける。その部品は、AI のフックで会話を空にできると名乗る。常駐は、名乗っていない参加者のリフレッシュリクエストを返すアクションバルクを断り、通ったら行った参加者に覚える。部品がターンの終わりに訊いたら、文の頭に `matomezu: ` を付けて 1 度だけ渡し、部品は会話を空にしてその文を打つ。利用者トリガートークがあっても捨てない。部品が会話を空にできなかったら、次のターンの終わりに AI に 1 度だけ伝える。覚えは常駐だけが持つ記録で、常駐を起動し直すと消える（引継ぎページは残る）
- その部品は、ワークルームに引継ぎ対象チケットがある間、ターンの終わりにターンを終わらせずに引継ぎページを書かせる（1 ターンに 1 度。続けさせるかと AI に渡す文は常駐に訊き、文はプラグインが書く）
- 参加者のセッションが終わったら退室させるかは、`clients/<AI の名前>/` が、どのプロセスの終わりをセッションの終わりと見るかを選ぶ（`matomezu mcp` の引数になる）。選ぶのは、そのセッション 1 つだけの物で、セッションの間は居て、終われば居なくなるプロセス（AI のプログラムのプロセスか、MCP のプロセス）。セッションの途中で入れ替わることがあるプロセスは、入れ替わったあと参加を頼み直せば同じ参加者に戻れるときだけ選んでよい。そう言えないときは名乗らない。確かめられないときは、退室させない

## 起こす知らせ

- 常駐は、起こす知らせを送り先の参加者ごとに、AI の側から渡せたと返るまで持つ。上限があり、古い物から捨てる。常駐を起動し直すと消える（常駐だけが持つ記録。「状態を変える所」）
- 常駐が渡せたと受けた知らせは、二度渡さない。渡せたと受けていない物は、もう一度渡ることがある（少なくとも 1 回届く）
- AI の側で知らせを渡す物は、渡せた・その会話がその AI のプログラムに無い・失敗のどれかを答える。会話が無いと答えた知らせは、その参加者の呼び出しの返事で渡す
- 同じ参加者への知らせは、送った順に渡す
- 送り先が参加者でなくなったら捨てる。引き継いだ参加者には渡さない
- AI 間メッセージを送れるのは、参加が確定してワークルームに入っている AI だけ（ビジターは送れない）。送り先も同じ。送り手は呼び出しの参加者（アクションの `run` が返して送るときは、行った参加者。「定義と機能台帳」の「アクション」）から決め、引数では受けない
- 封筒は matomezu ペイロードと AI 間メッセージを 1 通ずつ運ぶ（利用者が送り手の物には、送り手のワークルームが無い）。封筒の形は、ほかのホストへ運ぶときも変えない。同じ id の封筒は二度入れない
- AI ラリーは、受けるホストの常駐が、送り手から送り先への向きごとに数える。上限を超える AI 間メッセージは届けずに断る（送り手には断りの答え、送り先には止めた事を 1 度だけ知らせ、数が戻ってまた届くときは、その事を先に知らせる）。数は、どちらかの AI に利用者トリガートークがあったら 0 に戻し（利用者が送り手の matomezu ペイロードは数えず、それが送り先の AI に届いたときも同じに戻す。利用者トリガートークにはならない）、常駐を起動し直すと消える。ほかのホストからは、送り手のホストが送り手の側の数を封筒に載せ、受けるホストは両方の数が上限を超えたときだけ断る。上限は、同じホストの中は決まった数、ペアリングしたホストから届く物は、受けるホストの利用者がホストごとに決める
- 封筒の送り先と送り手は、ホスト（ホスト id）とワークルームの名前で書く。送り先の参加者は、受けたホストが引く。ほかのホストから届いた封筒は、送り手のホストが、相手のホストの鍵（「ホストとブラウザとのやり取り」）と違えば断る（書き換えない）
- ほかのホストの AI からの知らせには、送り手のホストを、ホストエイリアスで添える
- 利用者の頼みとして受ける行には、印を付ける。印の付いた行だけが、起こす知らせの中で利用者の頼みになる。当たるのは、利用者の頼みとして受けるホストからの AI 間メッセージと、利用者の選んだ管理者のワークルームから同じホストへ送る AI 間メッセージ（受け入れのアクションが書いた管理者の印は数えない。「参加者」）と、窓から利用者として行ったアクションが送った matomezu ペイロード（「定義と機能台帳」の「アクション」）と、利用者が画面で押した常駐の口の頼み（管理者に更新を頼む など）
- AI 間メッセージは、そのまま送り先に届ける。同じホストの中の AI 間メッセージは、承認待ちにしない（吹き出しも、承認・キャンセルも無い）。ほかのホストから届いた AI 間メッセージは、受けるホストの常駐が承認待ちとして持ち、参加者リストに承認待ちの吹き出しを出す（画面は常駐から受ける）。ただし、利用者の頼みの印が付く物（利用者の頼みとして受けるホストから届いた物）は承認待ちにしない。利用者が画面で承認すると、送り先に承認の知らせを 1 通起こし、その 1 通は利用者の頼みとして受ける。画面でキャンセルしたときは、承認待ちを外し、送り手と送り先の両方にキャンセルの知らせを起こす。送り先の AI がその送り手に AI 間メッセージを返したとき、送り先が参加者でなくなったときは、知らせずに外す。送り先の AI に利用者トリガートークがあっても外さない。承認・キャンセルは、その送り手から送り先への向きの AI ラリーの数を 0 に戻す（利用者が介入したとみなす）。承認待ちは常駐だけが持つ記録で、送り先 1 人ずつに上限があり古い物から知らせずに捨て、起動し直すと消える（「状態を変える所」）。承認・キャンセルの知らせの本文は、常駐メッセージと同じく英語で、送り手のホストは、この節の、ほかのホストの AI からの知らせと同じに添える。知らせは、どの 1 通かを、そのメッセージの本文の頭で示す
- 送り手へのキャンセルの知らせは、取り消す封筒の id と、その本文の頭を載せた封筒で、送り手のホストへ運ぶ（AI ラリーにも承認待ちにも数えない）。この封筒も、運ぶときに形を変えない
- 常駐メッセージは、行う者が利用者でも AI でも送る。アクションバルクが断られたら送らない。送り先が行った AI 自身のワークルームなら送らず、そのアクションの結果の知らせ（`notice`）で渡す。参加の確定した AI のいないワークルームへは送らない（断らない）
- 常駐メッセージの本文は英語で、利用者の言語に合わせない。送り手を matomezu と示す頭（`matomezu: `）は常駐が付け、本文はプラグインが書く

## 状態を変える所

- 状態を変えるのは `store` の中だけ（ほかで `setState` を使わない）
- データを変える入口はアクションだけ（画面の操作も AI の操作も同じアクションを通る。テストの用意を除く。「作業の進め方」の「テスト」）。常駐だけが使う記録（ブックを開いた時刻、参加者の様子など）は、アクションを通さず常駐が持つ。読めない物を読めない物のフォルダへ移す・戻す・そこから完全に消すのも、足りないシステムフォルダとバックヤードを足す・名前の重なりに番号を付ける・残れなくなった参照エントリを外すのも、アクションでなく、core の読む関数が決めて常駐が書く（「定義と機能台帳」の「ブック」「システムフォルダ」「バックヤード」）。アセットを入れるのは、アクションでなく別の口（画面の `/api/assets` と、AI の `import_image`）。アセットは、中身で決まる id の、書き換わらない置き場に、ブックのデータとは別に持つ。指してよいのはページだけで、書庫のどこ（ゴミ箱・読めない物のフォルダ・バックヤードも）からも指されないアセットは、常駐の起動のときに消える。アセットは `<img>` で描き、HTML・SVG として中に入れない
- 土台（core・store・ui）は、プラグインの物（アクションなど）を id で名指さない。アクションを行ってからステージで開く、のような組み合わせは、そのアクションを持つプラグインが関数で出す（base の `addPageIn`・`createBookIn`）。行うだけなら `perform`
- インスタンスの、`useActions` に入れない操作は、ホストクライアント・画面の入口（`main.tsx`）・土台のフックが使う。base のフックも、ホストに頼む読み取り（横断検索と、追加プラグインを無効にしたら読めない物のフォルダへ移る物を数える事と、完全に消すページをスクラップで指しているページを引く事。結果は画面の状態に入れず、呼んだビューに返すだけ）と、編集ロックの掛け外しと、ブラウザの窓に頼む操作（クリップボードに書くなど）と、ホストに頼む書き込みと頼み（起動エラーの画面から追加プラグインを外すなど）に使う。base 以外のプラグインは、それらをプラグイン API のフックと、コマンドの run が受け取る操作を通してだけ触る。base のコマンドは、元に戻す・やり直すで、行わずに確かめる操作（`tryPerform`。プラグイン API に出さない）も使う

## ホストとブラウザとのやり取り

- ホストとブラウザに触るのは `host-client` だけ
- 起動の途中の失敗（常駐につながらない）は画面に出さない（起動していないことは利用者に分かる）。常駐につながらなければ、つながるまで待つ。ただし、次の 2 つのときだけ、ビルトインプラグインだけでインスタンスを作り、UI マッピングで描いて止める。常駐は立っているのに、このブラウザが画面 cookie を持たず断られたとき（ブックと設定を読まず、開き方の案内を描く。立っている常駐を待っても、利用者には原因が分からないため）と、追加プラグインのどれかを組めず、画面が起動を止めるとき（起動エラーの画面を描く。「プラグイン」の「`core/catalog.ts`」）。起動エラーの画面の窓は、AI の `view`・`show` の向け先に数えない
- 常駐の「画面から」の入口（HTTP）は、画面 cookie を持つブラウザの頼みだけを通す。AI の入口とは別で、AI は画面の入口を使えない。画面 cookie の鍵を渡す使い捨てのコードは、常駐がブラウザを開く URL にだけ載せ、どの返事にも載せない。入口を足すときは `screen` で包む（テストが見張る）
- ホストどうしの入口は、画面から・AI からの入口とは別で、利用者の設定でほかのホストとつなぐときだけ開く。つながない間は、ペアリングしたホストへも頼みに行かない。相手のホスト id は、TLS で見せたホストの鍵（リバース接続の上では、その中で結んだ TLS の鍵。外の接続で確かめた相手と違えばつながない）から決め、頼みの中の申告では決めない。口は `peer.Pinned`（ペアリングしたホストだけを通す）か `peer.Unpinned`（鍵を知らない相手も通す）で包み、`Unpinned` はペアリングの頼みの口 1 つだけが使う（テストが見張る）。鍵を覚えるのはペアリングだけで、届いた頼みは、利用者が接続確認コードを見比べて受け入れるまで覚えず、同じ LAN で見つけただけのホストの鍵も覚えない
- Windows で直に動く常駐は、利用者が Windows のファイアウォールで matomezu を許可している間だけ、LAN のやり取り（ホストどうしの入口で待つ・mDNS で名乗る・見つける・リバース接続を張る・ほかのホストへ頼みに行く）をする。許可するまで LAN で待たない（Windows の許可のダイアログを出さない）。待つのは、規則を付けたポートで、IPv4 だけにする（規則は IPv4 の相手で絞る）。NAT の WSL の常駐が Windows に立てる WSLプロキシも同じにする【未実装】
- 常駐間通信プロトコルを変えたら、その版（`peer.Protocol`）を上げる。ただし、フィールドを足すだけで、古い版の相手がそれを捨てても今のまま動き、新しい側がそのフィールドの無い相手の読み方を決めているときは上げない（今あるフィールドに値を足すのは含めない）。口の道の `/peer/v1` は変えない（版はヘッダで運ぶ）
- WSL と WSLプロキシの間のやり取りを変えたら、その版（`peer.WSLProxyVersion`）を必ず上げる（`peer.Protocol` の、フィールドを足すだけなら上げない例外は無い。両方の版が同じことを前提にする）
- 窓は、スクリーンアレンジメントが名乗る枚数を超えた分のスクリーンを閉じる（「定義と機能台帳」の「スクリーン」）。窓を開いたときに開くスクリーンのほかは、ブックスクリーンも含めて 0 枚にできる。どれを見せるかは、スクリーンアレンジメントがその値とともに決め（見えているスクリーン）、キーが効く先は、カレントスクリーンの 1 枚。土台は、スクリーンの並べ方・大きさ・出入りの動きを決めない。カレントでない・見えていないスクリーンの中は残す。見えていないブックスクリーンの物は、見えていない物として分けて AI に知らせる
- スクリーンを開くのと、描かれているスクリーンを閉じる・渡す値を替えるのと、スクリーンアレンジメントを替えるのは、ビューはプラグイン API のフックで、コマンドは run が受け取る操作で行う（ほかのスクリーン・ステージを id で名指せる物は「プラグイン」の「プラグインどうしの関係」）
- 画面の場所は、ホストクライアントがブラウザの URL と行き来させる。ブック・ページの移動と分割する・やめる、スクリーンを開く・閉じる・開いている 1 枚の渡す値を替える、カレントスクリーンとスクリーンアレンジメント（値も）の変わりと、画面の場所に入れて積むと宣言したプラグイン状態の値の変わりはブラウザの履歴に積み、ほかは（書き換えると宣言したプラグイン状態も）書き換えるだけ。同じ同期の処理の中の移動は、まとめて 1 つ積む（await・setTimeout の後は別に積む）。利用者の操作でない移動（窓の大きさでスクリーンアレンジメントを戻すなど）は積まない。積まないと頼む操作で指定する。選択と道具は入れない
- ブラウザの履歴を 1 つ戻すのは、この窓が積んだ行の中だけ（窓の外へは出ない）。ビューはプラグイン API のフック（`useBrowserBack`）で、コマンドは run が受け取る操作（`requestBack`）で頼む
- 窓は、開いたときと dataVersion（matomezu 保管庫フォルダのデータの形の番号）が違う常駐につながったら、読み直すまでデータを変える頼みを送らず、確かめられていないアクションも送り直さずに捨てる
- ホスト（常駐サーバー。Go）は、アクションを `web/src/engine/engine.ts` から作った `internal/engine/engine.js` で行う（ホストのエンジン）
- ホストは、つながっている窓ごとに、見ているものとフォーカスの順を覚える。AI の `view` と `show` は、見ているものを知らせた窓のうち最後にフォーカスされた窓に向ける。最後にフォーカスされた窓（開いた直後の窓など）がまだ知らせていなければ、上限の時間まで知らせを待つ
- ゴミ箱の物・読めない物のフォルダの物（ブック・フォルダ・ページ・バインダ）・確かめる関数が開けないとしたブック（「warning」）と、そのアノテーションは、AI の MCP 公開ツール（`list_books`・`read_folder`・`read_book`・`read_page`・`read_image`・`view` が添える、AI の応えを待つ物・`show`）と CLI の `annotations` に出さない。読めない物のフォルダの物と開けないとしたブックを名指したアクションと `read_page`・`read_image` は、「無い」（`no-book`・`no-page`）で断る。アセットはページを名指して見せ、アセットの id では AI に見せない（見せない物のページが指すアセットを見せないため）
- バックヤードとその中のブックは、AI の一覧（`list_books`・`read_folder`・AI の応えを待つ物）に出さない。中のブックとページは、id を知っていれば `read_book`・`read_page` で読め、アクションで名指せる。ただし `read_folder` は、呼んだ AI のワークルームの作業机と、その下に映す、今の作業のワーカーブックを出せる。そのワーカーブックの、AI の応えを待つ物も、その AI に出す。`read_records` の全文（`id`・`ids`）は、そのレコードを `workKey` に持つ、AI に見せると名乗ったバックヤードの中のブックを、id とページの数だけで添える（一覧の行と、開けないとしたブックには添えない）
- どこかの窓に出ているステージエントリ（見えていないブックスクリーンの物も含む）を、AI はゴミ箱に入れられない（`open-on-screen` で断り、何も変えない。AI は利用者に聞く）。開いた時刻を残すのは、窓で見えたブックだけ
- どこかの窓で利用者が直している物（ブックの中の物・アノテーション・レコード。編集ロック）を、AI のアクションは変えも消しもしない（`being-edited` で断り、何も変えない）。利用者のアクションは編集ロックで止めない。ただし `lockedForUser` のアクション（変更提案郵便の反映など、直している最中に当てるとその直しで上書きされる物）は止める。フォローステップが応じて変える物（バックヤードの中の物も）が編集ロックの物なら、行う者を問わず止める
- AI 編集チケットは、AI の `perform` の 1 回（アクションバルク 1 つ）に 1 つ開き、変えたページ・ブック・バインダが全部、窓で見えたら閉じる。見られる前に、利用者の画面の履歴に入らない変更（ゴミ箱から消すなど）で消えたら、消えたことを AI に渡す。戻す・やり直すが AI の変更とぶつかって断られたときは（「定義と機能台帳」の「アクション」）、AI の変更が残り、消えたとは渡さない。アクションが失敗にした・郵便が消えたと記した AI 編集チケットは、次の利用者トリガートークのときに AI に渡る。AI 編集チケットの数には全体で上限があり、古い物から捨てるが、`key` で見分ける物（アクションが返した物）は捨てない

## OS の設定を変える所

- OS の設定（Windows のファイアウォールの規則など）を変えるのに OS の管理者の権限（Windows の UAC など）を求めるのは、利用者が押したときだけで、その操作につき 1 回にする。立ったときなど、利用者が押さずに求めない
- 昇格して流す中身はコードに固定し、受け取るのは決まった形に確かめられる値（操作の別・数）だけにする。文字列で組んだコマンドや、利用者・相手のホストから届いた文字列を昇格して流さない。中身はファイルに書かずに渡す（書いてから流すまでの間に書き換えられないため）

## error

- 投げる error は `core/errors.ts` の表に番号（E と 3 桁）と文を書き、`problem`・`fail` で作る。ほかで `new Error` を作らない（同じクレートの中で捕まえる合図（`NoServer` など）は error ではないので除く）
- 台帳アセンブルの error では、ビルトインプラグインならインスタンスを作らず、追加プラグインなら、ホストはそのプラグインを足さず（起動のときは外して立つ）、画面は起動を止める（「プラグイン」の「`core/catalog.ts`」）。実行中の error は、その操作を止める
- 番号は一度付けたら変えず、消した番号も使い回さない。範囲は E0xx 定義の組の食い違い、E1xx 表に無いものを引いた・前提の状態が無い、E2xx 画面の組み立て、E3xx プラグイン、E4xx ホストとブラウザとのやり取り
- 文は開発者向けの英語で、画面には出さない（起動エラーの画面は、起動を止めた理由の文を出す。読むのはプラグインの作り手のため）
- アクションが断る理由（`unknown`・`not-allowed` など）は結果であって error ではないので、表に入れない

## warning

- warning は、その組み合わせ（プラグイン・ブック・UI マッピング）である間ずっと成り立つ問題に使う。画面で見つかっても常駐で見つかっても、そうした問題は warning に落とす。一度きりの出来事（アクションを断られた・通信が切れた・描くときの例外）は warning にしない（断りはトーストかダイアログ、error は E、調べるための記録はログ）
- 止めるほどではない間違い（その物だけ効かない）は、error にせず warning にする。warning は `core/warnings.ts` の表に番号（W と 3 桁）と文を書き、どのプラグインの warning かを添えて、台帳アセンブルが機能台帳に集める
- 番号の決まりと文は error と同じ（変えない・使い回さない・開発者向けの英語で画面には出さない）
- 追加プラグインの既定のキーバインドが、同じ範囲・同じキーのほかのプラグインのキーバインドに負けて効かないときは、warning にする（利用者のキーバインドに負けたときは warning にしない）
- ビルトインプラグインは warning を出さない（テストが見張る）
- 読めない物は、ブック（ブックの形に合わない・並びや id の決まりを守らない）と、ページ（機能台帳に無いタイプ・タイプの形に合わない・タイプの決まりやアイテムどうしの決まりを守らない）。入れるタイプが機能台帳に無い・形に合わない・決まりを守らないバインダは、バインダごと読めない物にする。ブックの外の決まり（「定義と機能台帳」の「ブック」）を破るページとバインダも、読めない物にする。読めない訳は warning の番号で持ち、物ごとの warning にはしない。warning にするのは、読めない物のフォルダに物が在る事の 1 つで、件数と訳ごとの数を添える。中に読めない物が残っているブック（読めない物のフォルダへ移る前）は、確かめる関数がブックごと開けないとし（読めない物には数えず、移さない）、ブックごとの warning にする。確かめる関数は core に 1 つだけ置き、画面もホストも使う
- 読めるが、機能台帳に無いアイテムや設定の項目を持つブックとブックの外のページも、warning にする（どのプラグインの warning かは、無い物の持ち主）
- 画面だけで見つかる warning（UI マッピングで飛ばした物・`place` の `before`・`after` の書き方が合わずに置かなかったウィジェット）は、ホストクライアントがホストに知らせる（前に知らせたものと入れ替え、つなぎ直すたびに知らせ直す）。知らせるのは番号と値だけで、文はエンジンが表から作る
- ホストは、問題を 1 か所にメモリで持つ: 定義の warning・読めない物のフォルダに在る物・書庫を整えるのに失敗した事・warning のあるブックとブックの外のページ・書庫の木の決まり（定義と機能台帳の「ブック」）が破れている事・画面が知らせた warning（窓ごと。窓が離れたら消す）。起動したときとプラグインが変わったときに全部のブックとブックの外のページを、保存されたときにそのブック（ブックのページ・バインダ・ブックの行が保存されたとき）かそのページを確かめ直す。書庫の木の決まりは、起動したときと、木が変わりうる保存のあとに確かめ直す（読めるかは今の機能台帳で決まる。読めるかで決まる物のうち DB に残るのは、読めない物のフォルダへ移した事だけで、機能台帳が変わるたびに決め直す）。ゴミ箱の中の物の問題は出さない（ゴミ箱から戻したら出す）
- ホストは問題を、常駐のログ（変わったときに書く）と、AI の `actions` に出す
