# 構造とクレート

## クレート

`web/src` の下を、役割ごとのクレートに分ける。`web/src` の直下には、表のクレートと画面の入口（`main.tsx`）・`css.d.ts` だけを置く。

| クレート | 役割 | 読んでよいもの |
|---|---|---|
| `core` | データの形・定義の型・core 台帳・純粋な関数。React も状態も持たない | `core`・zod |
| `store` | 状態（Zustand）・コマンド・ダイアログの表・台帳アセンブル | `core`・`store`・zustand |
| `ui` | 画面の根と、プラグインが使う画面の口。画面に出る物は置かない | `core`・`store`・`ui`・React・zustand |
| `host-client` | ホストクライアント: 画面がホスト（常駐サーバー）とブラウザ（保存・URL・履歴・クリップボード・印刷）に頼む口 | `core`・`store`・`host-client`・zod |
| `engine` | ホストのエンジン: ホストの goja で、画面と同じアクションを行う入口 | `core`・`store`・`plugins`（ビルトインの一覧と、各プラグインの入口だけ）・`plugin-modules`・zod |
| `plugins` | 画面に出る物と、足していく定義の全部（ビルトインプラグイン） | 下の行（プラグインのファイルと、base 以外のビルトインプラグイン） |
| `plugin-api` | プラグイン API: 追加プラグインとビルトインプラグインが使ってよい名前を、土台から出し直すだけのクレート（`index.ts` は React なし、`ui.ts` は見た目、`builtin.ts` はビルトインだけが使うビルトインの印 `defineBuiltin`（キーバインドでビルトインを先に扱う）と、台帳アセンブルのときの確かめ（`checks`）を書く `CatalogCheckDef`・`problem`・`warning`、テーマキーに書かれた値の引き方 `writtenValues`） | `index.ts` は `core`・`store`、`ui.ts` は `ui`、`builtin.ts` は `store` |
| `plugin-entry` | プラグイン API の入口（`index.ts` が `matomezu`、`ui.ts` が `matomezu/ui`） | `index.ts` は `plugin-api`・zod（`z` を出し直す）・`plugins/base`（base の入口の名前を、一つずつ書いて出し直す）・`plugins/base/utils`（丸ごと出し直す）、`ui.ts` は `plugin-api/ui`・`plugins/base/ui`・`plugins/base/utils/ui`（丸ごと出し直す）。どちらもビルトインプラグインの一覧（`plugins`・`plugins/ui`）を型だけ読み、ビルトインが `core/catalog.ts` に書き足した物をいつも含める |
| `testing` | テストで組む入口（`matomezu/testing`）。テストのプロセスの中で組み、ホストは使わない。プラグイン API に含めない | `core`・`store`・`ui`・`plugins`（ビルトインプラグインの一覧） |
| `plugin-modules` | 追加プラグインが借りる、名前から実物を引く表（`index.ts` はホストのエンジン用、`ui.ts` は画面用） | `plugin-entry`・React |

- 土台（`core`・`store`・`ui`）は、プラグインを受け取って動かす枠と、その枠が決める言葉（スクリーン・ステージ・ページ・置いたアイテムの外枠など）を持ち、具体的な機能は持たない。プラグインを読まない
- 土台の中に、プラグインしか使わない処理を置かない。そうした処理は base が持つ。ただし、土台が外に出していない値（store の状態など）を読む物と、土台が確かめたことを根拠に型で示せない所を言い張る物は、プラグインしか使わなくても土台に置く。core と store のモジュールで、プラグインしか読んでいない物が無いことを見張る（ui はプラグインが使う画面の口なので除く）
- ステージの状態（道具のアイコンを開いているか・背景を直しているか）と、その開閉の決まりは、ステージの言葉として土台に置く。土台自身も読む状態で、上の行の「プラグインしか使わない処理」には当たらない
- コマンドマッピングの `anchorMenu`（押した物にアンカーがあるとき、どの右クリックのメニューにも足すコマンドの並び）は、コマンドマッピングの言葉として土台に置く。アンカーを付ける・押した物のアンカーを見つける・メニューに足すのは base で、土台は並びを確かめて渡すだけ
- プラグイン（base を含む）が画面の中で持つ状態は、プラグイン状態（`PluginStateDef`）として宣言する（ビューの中だけの一時の状態は「コードの書き方」の「データとビュー」）。範囲は、ステージ・スクリーン・窓（左サイドパネルの開閉など）のどれか。スクリーンの範囲の値は、開いた 1 枚ごとに持ち、閉じたら消える。値は土台の store の 1 か所に持ち、アクションのデータとは別で、アクションでは変えない。土台は値の中を読まない。ビューは kit と宣言を渡すフックで、コマンドは文脈の `pluginState` と run が受け取る `updatePluginState` で、スクリーンの定義と書庫アピアランスのメソッドは受け取る `read` で、自分の宣言だけを読み書きする（`useActions` の操作には入れない。持ち主は宣言の id の頭のプラグイン。ステージ・スクリーンの範囲の宣言は、呼ばれた場所のステージ・スクリーンの値）。宣言は、値を画面の場所（URL に写る）に入れるか（`address`）を答える。入れるなら、読み直しても戻り、外から来る値を読むための形（zod）を持ち、土台は宣言の形で確かめる（合わない値と宣言の無い id は落とす）。ブラウザの履歴に積むかも宣言が答える。入れないなら、値の型だけを持ち、読み直すと消える（画面の場所を当てはめても残る）。ほかのプラグインの宣言に値を入れるのは、画面の場所に入れる宣言（`address` を持つ）に、宣言の id と値で入れる道（`useSetPluginStateById`。スクリーンの宣言は、書き先を呼んだビューのスクリーンか、スクリーンの定義の id で指す）だけ。URL やホストクライアントに自分で書かない
- 入口（`plugin-entry`・`testing`）は外に名前を出すだけで、中のコードは入口を読まない
- 例外は `plugin-modules`。`plugin-entry` を読んでよいのは `plugin-modules` だけで、`plugin-modules` を読んでよいのはホストのエンジン（`engine/engine.ts`）と画面の入口（`main.tsx`）だけ
- 向きは 土台 → `plugin-api` → ビルトインプラグインと `plugin-entry` → `plugin-modules` の一方向。`plugin-api` はプラグインを読まない（base の物を出し直すのは `plugin-entry`）
- プラグインのファイルは役割で見る。見た目（`.tsx` と `ui.ts`）は `ui` と同じものを読んでよく、ほかは `core`・`store`・zod だけ
- 表と上の行で読んでよい物（zod・React・zustand）のほかに読んでよい外のライブラリは次だけ: Markdown を読むライブラリ（mdast-util-from-markdown・mdast-util-gfm・micromark-extension-gfm と、その型の mdast）、コードを色付けするライブラリ（refractor と、その型の hast）。ライブラリごとに決めた 1 つのファイルだけが読み、その型をプラグイン API に出さない（matomezu の形に移して出す）
- 上の 2 行は base だけ。base 以外のビルトインプラグインは、`plugin-api` と base の入口だけを読み、土台を直に読まない。見た目は `plugin-api/ui`・`plugins/base/ui`・react も読み（react-dom は読まない。追加プラグインが借りられる物と合わせる）、見た目でないファイルは `plugin-api`・`plugins/base/index`・zod だけ。状態は `plugin-api/ui` のフック（「プラグイン」の「プラグインどうしの関係」）で読む。base はプラグイン API を読まない
- 見た目でないファイルは、見た目を読まない
- `web/src` のファイルどうしも、値で読む輪を作らない（型だけ読むのは除く）
- これらは `test/rules.test.ts` が見張る

## Go のパッケージ

`internal/` の下を、役割ごとのパッケージに分ける（`internal/` の外の Go は、実行ファイルの入口 `cmd/matomezu`、埋め込む画面の `web`、AI の側の部品 `clients/<AI の名前>/` の下だけ）。読み込みの向きは一方向で、輪を作らない。

| パッケージ | 役割 | 読んでよいもの |
|---|---|---|
| `storage` | matomezu のデータ（ブック・設定など）の保存（SQLite）。ブックの中身は、ページとフォルダの行に分けるための土台のフィールド（エントリの種類・id、フォルダの役〈`folderRole`〉）のほかは解釈しない（一度きりのデータの移し替えは除く） | なし |
| `plugin` | 追加プラグインのフォルダ（`matomezu.json`）を読み、Go に組み込んだ esbuild で変換する | なし |
| `engine` | ホストのエンジン: `engine.js` を goja で動かし、アクション・組み直し・ブックとアノテーションの確かめを行う | `plugin` |
| `server` | ホスト: HTTP の口・知らせ（SSE）・窓・データをまとめる Hub | `engine`・`plugin`・`storage` |
| `mcp` | AI に matomezu を MCP 公開ツールとして渡すサーバー。ホストの AI の口（`/api/ai/...`）にだけ話す | なし |
| `home` | matomezu 保管庫フォルダ（利用者ごとに 1 つ） | なし |
| `browser` | URL を既定のブラウザで開く | なし |
| `web` | 実行ファイルに埋め込む画面（ビルドした `web/dist`） | なし |
| `clients/<AI の名前>` | AI のプログラムごとの事情を抱える部品（その AI のプログラムに起こす知らせを渡すなど） | なし |
| `cmd/matomezu` | 実行ファイルの入口。上のパッケージを組み合わせる | 全部（`web`・`clients` も） |

- `mcp` は `server` を読まない。AI からの頼みは、人の画面と同じくホストの HTTP の口を通す
- `clients` を読むのは `cmd/matomezu` だけ
- これらは `test/rules.test.ts` が見張る
- `server` がブックの JSON から直に読んでよいのは、土台のフィールド（ブックの名前、エントリの種類〈ページ・バインダ・読めないページ・ブック・フォルダ〉・id・名前、ページのタイプ、バインダが入れるタイプ、バインダの中のページ、フォルダの行の役（`folderRole`）・システムフォルダの印（`systemFolder`）と並び）と、役を名乗る種類（参加者・ワークルーム。`SubjectDef` の `role`）のレコードの、core が取り決めたフィールドだけ。アイテムやタイプのフィールドは読まず、中身の解釈はホストのエンジンに任せる（見張りは無い）

## AI の側に置く物

matomezu が配る AI ごとの部品（Claude Code のプラグインなど）は `clients/<AI の名前>/` に置き、その AI のプログラムの事情（プラグインの形・フック・会話への渡し方）を抱える。ほかの AI の部品は、`matomezu watch` の知らせを渡すコマンドの約束に合わせて、matomezu の外で作れる（matomezu が配る部品も、外の物に差し替えられる）。
起こす知らせの決まりと AI に見せる文は、常駐と、AI の種類を問わないコマンド（`matomezu watch` など）が持つ（その AI のプログラムに渡すための名前は除く）。

- 常駐は外のプログラムを起動しない。起こす知らせは、AI の側で受け取る
- 常駐と MCP は AI の種類を知らない。AI のプログラムごとに違う受け取り方（1 行の長さなどの値と、知らせを渡すコマンド）は `clients/<AI の名前>/` が持ち、`matomezu <AI の名前>` のコマンドがそれで `matomezu watch`（`matomezu mcp`）を組み立てる。AI ごとの部品は、AI のプログラムから `matomezu <AI の名前>` を呼ぶ
- 参加者のセッションが終わったら退室させるかは、`clients/<AI の名前>/` が、どのプロセスの終わりをセッションの終わりと見るかを選ぶ（`matomezu mcp` の引数になる）。選ぶのは、そのセッション 1 つだけの物で、セッションの間は居て、終われば居なくなるプロセス（AI のプログラムのプロセスか、MCP のプロセス）。セッションの途中で入れ替わることがあるプロセスは、入れ替わったあと参加を頼み直せば同じ参加者に戻れるときだけ選んでよい。そう言えないときは名乗らない。確かめられないときは、退室させない

## 起こす知らせ

- 常駐は、起こす知らせを宛先の参加者ごとに、AI の側から渡せたと返るまで持つ。上限があり、古い物から捨てる。常駐を起動し直すと消える（常駐だけが持つ記録。「状態を変える所」）
- 常駐が渡せたと受けた知らせは、二度渡さない。渡せたと受けていない物は、もう一度渡ることがある（少なくとも 1 回届く）
- AI の側で知らせを渡す物は、渡せた・その会話がその AI のプログラムに無い・失敗のどれかを答える。会話が無いと答えた知らせは、参加の id の付いた呼び出しの返事で渡す
- 同じ参加者への知らせは、送った順に渡す
- 宛先が参加者でなくなったら捨てる。引き継いだ参加者には渡さない
- AI 間メッセージを送れるのは、参加が確定してワークルームに入っている AI だけ（ビジターは送れない）。宛先も同じ。送り手は呼び出しの参加者（アクションの `run` が返して送るときは、行った参加者。「定義と機能台帳」の「アクション」）から決め、引数では受けない
- 封筒の形は、ほかのマシンへ運ぶときも変えない。同じ id の封筒は二度入れない

## 状態を変える所

- 状態を変えるのは `store` の中だけ（ほかで `setState` を使わない）
- データを変える入口はアクションだけ（画面の操作も AI の操作も同じアクションを通る。テストの用意を除く。「作業の進め方」の「テスト」）。常駐だけが使う記録（ブックを開いた時刻、参加者の様子など）は、アクションを通さず常駐が持つ。読めない物を読めない物のフォルダへ移す・戻す・そこから完全に消すのも、足りないシステムフォルダを足す・名前の重なりに番号を付けるのも、アクションでなく、core の読む関数が決めて常駐が書く【未実装】（「定義と機能台帳」の「ブック」「システムフォルダ」）
- 土台（core・store・ui）は、プラグインの物（アクションなど）を id で名指さない。アクションを行ってからステージで開く、のような組み合わせは、そのアクションを持つプラグインが関数で出す（base の `addPageIn`・`createBookIn`）。行うだけなら `perform`
- インスタンスの、`useActions` に入れない操作は、ホストクライアント・画面の入口（`main.tsx`）・土台のフックが使う。base のフックも、ホストに頼む読み取り（横断検索。結果は画面の状態に入れず、呼んだビューに返すだけ）と、編集ロックの掛け外しと、ブラウザの窓に頼む操作（クリップボードに書くなど）に使う。base 以外のプラグインは、それらをプラグイン API のフックと、コマンドの run が受け取る操作を通してだけ触る。base のコマンドは、元に戻す・やり直すで、行わずに確かめる操作（`tryPerform`。プラグイン API に出さない）も使う

## ホストとブラウザとのやり取り

- ホストとブラウザに触るのは `host-client` だけ
- 起動の途中の失敗（常駐につながらない）は画面に出さない（起動していないことは利用者に分かる）。常駐につながらなければ、つながるまで待つ。ただし、常駐は立っているのに、このブラウザが画面 cookie を持たず断られたときだけ、ブックと設定を読まずにビルトインプラグインだけでインスタンスを作り、開き方の案内を UI マッピングで描いて止める（立っている常駐を待っても、利用者には原因が分からないため）
- 常駐の「画面から」の入口（HTTP）は、画面 cookie を持つブラウザの頼みだけを通す。AI の入口とは別で、AI は画面の入口を使えない。画面 cookie の鍵を渡す使い捨てのコードは、常駐がブラウザを開く URL にだけ載せ、どの返事にも載せない。入口を足すときは `screen` で包む（`rules.test` が見張る）
- 窓は、スクリーンを何枚でも開く（定義が名乗る枚数の上限は「定義と機能台帳」の「スクリーン」）。窓を開いたときに開くスクリーンのほかは、ブックスクリーンも含めて 0 枚にできる。どれを見せるかは、スクリーンアレンジメントがその値とともに決め（見えているスクリーン）、キーが効く先は、カレントスクリーンの 1 枚。土台は、スクリーンの並べ方・大きさ・出入りの動きを決めない。カレントでない・見えていないスクリーンの中は残す。見えていないブックスクリーンの物は、見えていない物として分けて AI に知らせる
- スクリーンを開くのと、描かれているスクリーンを閉じる・渡す値を替えるのと、スクリーンアレンジメントを替えるのは、ビューはプラグイン API のフックで、コマンドは run が受け取る操作で行う（ほかのスクリーン・ステージを id で名指せる物は「プラグイン」の「プラグインどうしの関係」）
- 画面の場所は、ホストクライアントがブラウザの URL と行き来させる。ブック・ページの移動と分割する・やめる、スクリーンを開く・閉じる・開いている 1 枚の渡す値を替える、カレントスクリーンとスクリーンアレンジメント（値も）の変わりと、画面の場所に入れて積むと宣言したプラグイン状態の値の変わりはブラウザの履歴に積み、ほかは（書き換えると宣言したプラグイン状態も）書き換えるだけ。同じ同期の処理の中の移動は、まとめて 1 つ積む（await・setTimeout の後は別に積む）。利用者の操作でない移動（窓の大きさでスクリーンアレンジメントを戻すなど）は積まない。積まないと頼む操作で指定する。選択と道具は入れない
- ブラウザの履歴を 1 つ戻すのは、この窓が積んだ行の中だけ（窓の外へは出ない）。ビューはプラグイン API のフック（`useBrowserBack`）で、コマンドは run が受け取る操作（`requestBack`）で頼む
- ホスト（常駐サーバー。Go）は、アクションを `web/src/engine/engine.ts` から作った `internal/engine/engine.js` で行う（ホストのエンジン）
- ホストは、つながっている窓ごとに、見ているものとフォーカスの順を覚える。AI の `view` と `show` は、見ているものを知らせた窓のうち最後にフォーカスされた窓に向ける。最後にフォーカスされた窓（開いた直後の窓など）がまだ知らせていなければ、上限の時間まで知らせを待つ
- ゴミ箱の物と読めない物のフォルダの物【未実装】（ブック・フォルダ・ページ・バインダ）とそのアノテーションは、AI の MCP 公開ツール（`list_books`・`read_folder`・`read_book`・`read_page`・`view` が添える、AI の応えを待つ物・`show`）と CLI の `annotations` に出さない
- どこかの窓に出ているブック（見えていないブックスクリーンのブックも含む）を、AI はゴミ箱に入れられない（`open-on-screen` で断り、何も変えない。AI は利用者に聞く）。ブックを開いた時刻を残すのは、窓で見えたブックだけ
- どこかの窓で利用者が直している物（ブックの中の物・アノテーション・レコード。編集ロック）を、AI のアクションは変えも消しもしない（`being-edited` で断り、何も変えない）。利用者のアクションは編集ロックで止めない。ただし `lockedForUser` のアクション（変更提案郵便の反映など、直している最中に当てるとその直しで上書きされる物）は止める
- AI 編集チケットは、AI のアクション 1 回に 1 つ開き、変えたページ・ブック・バインダが全部、窓で見えたら閉じる。見られる前に、利用者の画面の履歴に入らない変更（ゴミ箱から消すなど）で消えたら、消えたことを AI に渡す。戻す・やり直すが AI の変更とぶつかって断られたときは（「定義と機能台帳」の「アクション」）、AI の変更が残り、消えたとは渡さない。アクションが失敗にした・郵便が消えたと記した AI 編集チケットは、次の利用者トリガートークのときに AI に渡る。AI 編集チケットの数には全体で上限があり、古い物から捨てるが、`key` で見分ける物（アクションが返した物）は捨てない

## error

- 投げる error は `core/errors.ts` の表に番号（E と 3 桁）と文を書き、`problem`・`fail` で作る。ほかで `new Error` を作らない（同じクレートの中で捕まえる合図（`NoServer` など）は error ではないので除く）
- 台帳アセンブルの error では、ビルトインプラグインならインスタンスを作らず、追加プラグインならそのプラグインを外す。実行中の error は、その操作を止める
- 番号は一度付けたら変えず、消した番号も使い回さない。範囲は E0xx 定義の組の食い違い、E1xx 表に無いものを引いた・前提の状態が無い、E2xx 画面の組み立て、E3xx プラグイン、E4xx ホストとブラウザとのやり取り
- 文は開発者向けの英語で、画面には出さない
- アクションが断る理由（`unknown`・`not-allowed` など）は結果であって error ではないので、表に入れない

## warning

- warning は、その組み合わせ（プラグイン・ブック・UI マッピング）である間ずっと成り立つ問題に使う。画面で見つかっても常駐で見つかっても、そうした問題は warning に落とす。一度きりの出来事（アクションを断られた・通信が切れた・描くときの例外）は warning にしない（断りはトーストかダイアログ、error は E、調べるための記録はログ）
- 止めるほどではない間違い（その物だけ効かない）は、error にせず warning にする。warning は `core/warnings.ts` の表に番号（W と 3 桁）と文を書き、どのプラグインの warning かを添えて、台帳アセンブルが機能台帳に集める
- 番号の決まりと文は error と同じ（変えない・使い回さない・開発者向けの英語で画面には出さない）
- 追加プラグインの既定のキーバインドが、同じ範囲・同じキーのほかのプラグインのキーバインドに負けて効かないときは、warning にする（利用者のキーバインドに負けたときは warning にしない）
- ビルトインプラグインは warning を出さない（テストが見張る）
- 読めないブック（ブックの形に合わない・並びや id の決まりを守らない）と、読めるブックの中の読めないページ（機能台帳に無いタイプ・タイプの形に合わない・タイプの決まりやアイテムどうしの決まりを守らない）も warning にする。warning にはブックの id と名前を添える。読めないページの warning は、ブックと理由ごと（無いタイプは、タイプごと）に 1 つにまとめ、枚数を添える。無いタイプの warning だけ、そのタイプの持ち主のプラグインの warning にする。タイプが機能台帳に無いバインダも、中が読めないページだけ（1 枚以上）なら読める。確かめる関数は core に 1 つだけ置き、画面もホストも使う
- 読めるが、機能台帳に無いアイテムや設定の項目を持つブックも、warning にする（どのプラグインの warning かは、無い物の持ち主）
- 画面だけで見つかる warning（UI マッピングで飛ばした物・`place` の `before`・`after` の書き方が合わずに置かなかったウィジェット・画面が組めずに外した追加プラグイン）は、ホストクライアントがホストに知らせる（前に知らせたものと入れ替え、つなぎ直すたびに知らせ直す）。知らせるのは番号と値だけで、文はエンジンが表から作る
- ホストは、問題を 1 か所にメモリで持つ: 定義の warning・読めないブック・読めないページ・warning のあるブック・書庫の木の決まり（定義と機能台帳の「ブック」）が破れている事・画面が知らせた warning（窓ごと。窓が離れたら消す）。起動したときとプラグインが変わったときに全部のブックを、ブックのページ・バインダ・ブックの行が保存されたときにそのブックを確かめ直す。書庫の木の決まりは、起動したときと、木が変わりうる保存のあとに確かめ直す（読めるかは今の機能台帳で決まる。読めるかで決まる物のうち DB に残るのは、読めない物のフォルダへ移した事だけで、機能台帳が変わるたびに決め直す【未実装】）
- ホストは問題を、常駐のログ（変わったときに書く）と、AI の `actions` に出す。読めない物は AI に見せず、名指したアクションと `read_page` は「無い」（`no-book`・`no-page`）で断る【未実装】
